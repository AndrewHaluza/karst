## [@ui:LAYOUT-SANITY] Layout-sanity gate

The `layout` Playwright projects run inside the existing `visual` UAT gate (`test:visual:docker`): one docker run, no second gate. They open EVERY Settings route with the `realistic` corpus, and every other registered view x variant (`ui:VISUAL-VARIANTS`, route id `<view>/<variant>`; new failures there are ledgered, not fixed, in the backfill), (`tests/visual/realisticSettings.ts`: 2 repos, 3 presets, pinned roles, local + approach profiles, a 40+ line profile body, a 60+ char model id, a 40+ char preset name; `empty` is the 0-presets/0-profiles state) and measure geometry. jsdom has no layout engine (`docs/ui/UI-INVARIANTS.md`: no layout, no paint), the screenshot sweep baselines whatever renders, and the property sweeps judge rules, not geometry. There are no baselines here, so a buggy page cannot be re-recorded into "correct".

- **Routes**: one per `SETTINGS_SECTIONS` member (reached by clicking the nav entry; there is no section deep link) plus the 7 Agents hashes (`#agents/roles`, `/roles/<role>`, `/roles?compare=<preset>`, `/profiles`, `/profiles/<long local>`, `/profiles/<approach>`, `/profiles/builtin:<role>`). `settingsRoutes.test.ts` fails when a section is missing.
- **Widths**: 1280, 900, 700, 699, 480 at height 900: both sides of the tier boundary plus a narrow split. Token usage adds 360 (`USAGE_EXTRA_WIDTHS` in `layoutBreakpoints.ts`) because its by-ticket table becomes cards at the tight tier. Tiers (`src/ui/layout/layoutBreakpoints.ts`): wide >= 1000, mid 700-999, narrow <= 699. `layoutBreakpoints.test.ts` pins the `@media` widths of the CSS files in `BREAKPOINT_PINNED_FILES` to those constants; the list is empty today (existing settings CSS uses 1024/768/800/700px) and grows as CSS migrates.
- **Scope**: a local gate runs only the routes of the selected views; CI runs every route (`ui:LAYOUT-SCOPE`).
- **Dark only**: geometry is theme-independent, so the `layout` project runs once, in dark.
- **Projects**: `layout-setup` clears `tests/visual/.layout-shards/`; `layout` (`*.layout.ts`) runs one test per route x width and writes a shard, never failing on geometry; `layout-teardown` merges the shards into `tests/visual/.layout-report.json`, applies the ledger and fails on a new or stale entry. Filter a run by FILE or by `KARST_UI_GREP`, never `--grep`: a CLI title filter can drop the teardown test. With `KARST_LAYOUT_MERGE=1` (CI only, `tests/visual/layoutShards.ts`), setup keeps the shards, and the teardown fails when an expected route x width has no shard file.
- **Checks** (1px tolerance, pure functions in `src/ui/layout/layoutChecks.ts`, each with a positive and a negative unit fixture):
  - a `page-overflow`: `scrollWidth > clientWidth + 1`.
  - b `sibling-overlap`: in-flow siblings (static/relative/sticky) intersecting by more than 1px on both axes.
  - c `containment`: an in-flow element extends more than 1px outside a parent whose overflow is visible. Scroll containers and absolute/fixed children are exempt.
  - c2 `scroller`: every scroll container lies inside the viewport and its pane (`data-region` root, else the page); at most one per pane.
  - d `clipped-text`: overflow hidden/clip with scroll size over client size. Allowed only with `text-overflow: ellipsis` AND the full text in `aria-label`, `aria-describedby` or `aria-expanded` (UI-R19: `title` alone does not count). The sr-only 1x1 pattern is not text.
  - e `column-alignment`: in `table`/`grid` roles, each body row's i-th cell left edge equals the header's within 1px. Rows with `colspan` are skipped, and so is a table whose header is hidden with the sr-only 1x1 pattern (the tight tier's card rows have no visible columns to align).
  - f `degenerate-control`: an icon-only control under 24x24 (`--k-hit-min`), a text control under 20px high, or any control outside the viewport horizontally. Native checkbox/radio boxes are exempt.
  - g `region-order`: per route, `tests/visual/expectations/<section>.json` lists `data-region` names in expected order per tier, side-by-side or stacked, and the primary action (`k-btn--primary`) must sit in the `header` or `toolbar` region (UI-R40). No `data-region` exists yet, so no expectations file ships and every route reports "unchecked", which is not "passed". Placement is not covered until a page adds its landmarks.
  - h `section-spacing`: the gap between sibling `<section>`s must exceed the largest gap between items inside one. Sections a grid places side by side (different left edge) are not compared.
  - i `state-survives-resize`: on each Agents hash, resize 1280 to 480 to 1280; the hash and the selected item are unchanged.
- **Output**: failures print grouped as route, width, check, selector, numbers (teardown test output), and the full list is in `tests/visual/.layout-report.json` (gitignored with the shards).
- **Ratchet ledger** `tests/visual/layout-known-failures.json` is the only exemption (no per-element opt-out attribute). Keys are `route|width|check|selector`. A failure not in the ledger fails the gate; a ledger entry that no longer reproduces ALSO fails the gate. Stale entries are judged only over routes x widths that ran, so a view-scoped run never reports an entry of a route that did not run. Docker is authoritative (host rendering differs): `npm run test:layout:docker:seed` seeds once (refused if the file exists), `npm run test:layout:docker:prune` removes stale entries only and never adds; both refuse on a filtered run and without `KARST_LAYOUT_AUTHORITATIVE=1`. Host `npm run test:layout` is advisory and cannot seed or prune. Never reseed to make a branch green.
- **Gate**: `scripts/visual-sweep-gate.mjs` runs only in CI, on the full chain. CI runs the `layout` tests in two shards and the verdict once, over the union of their shard files, so the verdict sees every route (`ui:RUNNING-SWEEP`). It fails when `layout` ran zero tests, when `layout-teardown` did not run exactly one test, or when a `layout`/`layout-teardown` test is `unexpected`. In the other projects it also fails a **pull request's own** added/changed baseline that does not match its screenshot (`ui:RUNNING-SWEEP`); every other screenshot diff stays advisory.
- **Cannot catch**: a wrong control in a sane-looking place (until a page ships region expectations), wrong copy, wrong colours, or a layout bug that only appears in a state the corpus does not render (add the state to the corpus).

## [@ui:LAYOUT-SCOPE] Layout chain scope in a local gate

- **Scope**: `scripts/dockerGate.mjs` narrows `test:visual:docker` and `test:layout:docker` to the views that the ticket diff reaches (`selectViews`, `gateGrep` in `scripts/uiViews.mjs`). A repeat pass with a usable state narrows further: to the views of the delta since the stored run, plus the failed tests of a red run (`scopedSelection`, `@arch:GATE-REPEAT`). The failed-test titles join the same grep, so the bookends still run and the ledger verdict judges only the routes that ran. The `layout` project uses the same `KARST_UI_GREP` grep. `layout-setup` and `layout-teardown` take no filter, so the ledger verdict still runs on the selected routes for any grep, and a filtered seed or prune is refused. The selection line states the scope, with counts that include layout tests. These runs stay on the full chain: CI (variable unset), `test:ui:docker` (it passes `KARST_UI_GREP: ''` because its view is named by hand, not derived from the diff), a shared path (a move counts as both of its paths), `playwright.config.ts`, a change to the ledger (it also voids the repeat-pass skip, `@arch:GATE-REPEAT`), an unknown diff, seed and prune. CI is the backstop for a layout bug that a view-scoped run misses.
- **No selected route**: `catalog` and `status` have no layout route. In that selection, `test:layout:docker` prints a skip line and exits 0 (but not when it carries failed tests of a red run), and in `test:visual:docker` the teardown accepts zero shards only if the grep matches no layout title. A run with selected routes and no shards still fails.
- **Measured saving**: `docs/issues/2026-11-06-layout-chain-narrowing-timing.md` (`@issue:NARROW-01`).
- **Fixture pages**: the fixture pages follow the same selection (`@ui:FIXTURE-SCOPE`).
END_DOC_BLOCK: [@ui:LAYOUT-SCOPE]

## [@ui:FIXTURE-SCOPE] Fixture pages of a scoped local run

- **The variable**: `KARST_VISUAL_FIXTURE_VIEWS` is a comma list of corpus view ids (`tests/visual/corpora.ts#ALL_VIEWS`). `tests/visual/writeFixtures.ts` writes the pages of those views only, and always writes `catalog.html`. Unset or empty means every view. An unknown id also means every view, with a warning. The webServer prints `Fixture views: all` or `Fixture views: <list>`.
- **Who sets it**: `narrowSweep` in `scripts/dockerGate.mjs`, from the same selection that builds `KARST_UI_GREP` (`fixtureViews` in `scripts/uiViews.mjs`; `status` maps to `dashboard`). The flake re-run and the base re-run inherit it. Part (a) of `test:ui:docker` sets its view.
- **Every page is written for**: CI (unset), a full selection, a red-run carry of failed tests (a failed title can come from any spec), a catalog-only selection, a hand-written `KARST_UI_GREP`, seed and prune, the `:update` scripts, and part (b) of `test:ui:docker`.
- **A missing page**: `gotoView` throws an error that names the page and the repair when the server answers 404 (`missingFixtureMessage`, `tests/visual/fixtureScope.ts`).
- **Guard**: `scripts/uiViews.integration.test.mjs` maps each test of the real listing of each view to the page view that it loads, and fails when `fixtureViews` leaves it out or a spec file is not in the map.
- **Where the pages go**: the docker gate scripts set `KARST_VISUAL_TMP_DIR=/tmp/karst-visual-fixtures` (`tests/visual/fixtureDir.mjs`; it accepts only a `karst-visual-*` directory directly in the temp directory and throws for any other value), so the pages (about 1 GB) stay on the container disk, not on the macOS bind mount, and `--rm` removes them. Thus a failed docker run keeps no pages on the host. The HTML report, the PNG diffs and `test-results/` stay on the host. To look at a page, run `node tests/visual/serve.mjs` on the host. A host run without the variable uses `tests/visual/.tmp`.

## [@ui:VISUAL-VARIANTS] Variant matrix (UI-R57)

`tests/visual/variants.ts` is the single registry: `view -> variants`, each with
a corpus builder (reusing the `renderFixtures` modules and `realisticSettings.ts`;
fixed data, no clock), a baseline name, the theme projects that record it, and a
layout target. `buildFixture.ts` writes `<theme>/<view>--<variant>.html` for each,
`pages.visual.ts` screenshots each, `layout.layout.ts` opens each distinct page at every width.

- **One layout run per page**: `layoutPlan()` keys a variant by its layout identity (`layoutIdentity()`: the view, its widths, the corpus messages and view state with ISO timestamps ignored, and `clicks`, the only step `layout.layout.ts` runs). A variant with the key of an earlier variant shares that run, so `width`, `themes`, `capture`, `viewportHeight`, `click`, `pills`, the popover and drawer steps, and the fill/reply steps never add layout tests. Example: `dashboard/inside-<stage>-<case>-mid|narrow|tight` share the run of `dashboard/inside-<stage>-<case>`. When `layout.layout.ts` starts to run a new step, add it to `layoutIdentity()`. `skipLayout` stays for a variant whose page differs but must not get a layout run.

- **Mandatory per view**: `populated`, `empty`, `loading` (no host message yet), `error`, `long-content`.
- **Theme split** (gate runtime): `populated` and the legacy dashboard stages and agents shots record `dark`, `light`, `hc`; every other variant records `dark` only. Geometry runs dark only. Grayscale and reduced-motion stay on the status spec (UI-R28, UI-R30).
- **Matrix size**: 9 views, about 110 variants (39 are the dashboard Inside matrix); about 110 dark shots plus 3 x ~15 light/hc shots, and 5 widths per variant for geometry. Update this line when it moves a lot.
- **Stage chip tiers (T1099)**: `sidebar/stage-chip-{460,300}` and `dashboard/stage-chip-{460,300}` record the one stage chip (@ui:11.21) at a full-word host and a short-word host, dark and light.
- **Queue relation (T1104)**: `sidebar/queue-chips-{460,300}` record the open Queue pane with the verb and chip of each reason (`Waits on` with `+N`, `Unblocks` with the raised arrow, `Cycle with`): one line at 460px, a second line at 300px, dark and light (@ui:UI-R57).
- **Waits on references (T1103)**: `sidebar/waits-on-{460,300}` record a row with three references ("Waits on", one chip, a `+N` button), one reference and none, dark and light (@ui:UI-R57).
- **Inside case registry**: `src/ui/dashboard/insideCases.ts` lists every stage x state case of the dashboard Inside block as a full `DashboardState`; each registers as the dark-only variant `dashboard/inside-<stage>-<case>`. Views come from fixed store rows through the real reducers (`insideCaseFacts.ts` -> `buildGateSwitches` + `buildInsideViews`); cases marked HAND-WRITTEN reuse a `renderFixtures.ts` view (no selector input exists). Ship preview cases alias the older `confirm-ship`/`ship-blocked`/`ship-error` variants (`aliasOf`, ledger-keyed, no second baseline). `insideCases.test.ts` fails when a stage lacks pending/running/passed, or uat/review lack the looped cases (2+ rounds, selected round, an older round selected, and an exhausted 3-round case with an older round selected). Baselines record current behaviour, bugs included.
- **Baseline names**: legacy names are kept (`sidebar.png`, `dashboard-running.png` for dashboard `populated`, `agents-*.png`); new ones are `<view>--<variant>.png`.
- **`error` without a host failure state**: gettingStarted has none, so its `error` variant is the fresh checklist; replace it when a failure state exists.
- **Not covered**: the doctor has no webview (`src/ui/doctor/host.ts` only), so it is not in `WEBVIEW_NAMES`.
- **Capture mode**: a variant is a full-page shot by default. A variant of a fixed overlay sets `capture: 'viewport'` and the shot is the viewport (`fullPage: false`, `screenshotFullPage` in `variants.ts`). A full-page shot of a fixed overlay also records the height of the page below it, so every dashboard height change moved all 24 `ticket-details-*` baselines (T1060, T1064, T1069). The dashboard keeps its own full-page variants, so its height stays covered. Only the ticket-details drawer uses it. If the drawer scrolls inside itself, the viewport shows its top.
- **Adding a variant**: add it to the registry, run `npm run -s test:visual:docker:update`, review the new PNGs only, run `npm run -s test:layout:docker` and ledger new failures with the owner's approval. `variants.test.ts` names what is missing, and `sweepBudget.test.ts` names the budget to update (`@ui:SWEEP-BUDGET`).

## [@ui:SWEEP-BUDGET] Sweep budget ratchet

`tests/visual/sweepBudget.ts` pins, for each view, the number of screenshots (variant x declared theme project) and layout tests (distinct page x width, plus the settings routes) that the view adds to the visual gate. `sweepBudget.test.ts` (unit gate) fails when a count moves. Above the budget: share a layout run, drop a theme, or raise the number with a reason (ticket and why) in a comment on that line. Below the budget: lower the number.

- **Why**: the sweep has one host slot and a 45 min limit (`UI_GATE_TIMEOUT_MS`), and each later ticket pays for every test a change adds. Before the budget, one change (#1066) took the sweep from 4,635 to 7,166 tests and passed every gate; the only answer was a higher CI limit.
- **Counts come from the registry**, not from a Playwright run, so the check costs about 1 s.

## [@ui:LIMITATIONS] Named limitations

- **xterm masked (D12)**: Dashboard terminal region is masked in screenshots. `injectXterm` needs `dist/vendor/xterm` and renders a canvas seeded by a live pty — nondeterministic by nature.
- **Catalog is documentation-only (D15)**: `KARST-UI-CATALOG.html` has its own hard-coded palette and cannot be themed. Baselines prove what the catalog claims, not what ships.
- **High-contrast-light excluded (C4)**: Not named by any rule; triples cost for no signal.
- **Corpus ratchet outstanding (C8)**: Seven non-dashboard views use MINIMAL state. FEAT-37 shrinks the ratchet. The standalone `serverLogs` panel is not one of them: it seeds through its own `server-logs` protocol, not the generic `state` message.

## [@ui:RUNNING-SWEEP] Running the sweep

**Baselines are container-authored.** `playwright.config.ts`'s `snapshotPathTemplate` carries no `{platform}` token, so the 85 PNGs under `tests/visual/__baselines__/` are valid for exactly one rendering environment: `mcr.microsoft.com/playwright:v1.63.0-noble`. macOS and Linux rasterize glyphs differently, so a bare `npm run test:visual` on macOS is a local smoke run and its diffs are not authoritative.

**Update baselines only with `npm run test:visual:docker:update`.** Never `npm run test:visual:update` on a developer machine, and never hand-edit a PNG. The image tag must stay in lockstep with the pinned `@playwright/test` version — a different tag ships a different Chromium and invalidates every baseline at once.

**CI runs the same image.** `.github/workflows/ci.yml`'s `visual` job is advisory for **pre-existing** screenshot **diff failures** while the suite settles: the Playwright exit code is published to the run summary, a run that executed tests with only pre-existing diffs does not fail the job, and the job uploads `tests/visual/.report/` as the `visual-report` artifact. Two things are never advisory: a sweep that executed **zero tests** — a webServer/startup crash, because `continue-on-error: true` used to record conclusion=success on a job whose sweep had never run (NDL-218) — and, on a pull request, a baseline the PR itself **added or changed** that fails its own screenshot (#769, how 9 sandbox-recorded baselines from #722 landed on develop and stayed red). `scripts/visual-sweep-gate.mjs` enforces both. Promote the remaining pre-existing failures to blocking — by letting the step exit with Playwright's code instead of the gate's verdict — once the sweep has run green on `develop` for a week with no baseline churn attributable to the environment.

**CI shards the sweep.** The job `visual-shard` runs 6 shards in parallel in the same image, with 1 worker each. `scripts/visual-shards.mjs` holds the plan and the measured times: `dark` in three parts, `layout` in two parts (`--no-deps`), and the other five projects in one shard. A split project uses `--fully-parallel --shard=i/k` with `PWTEST_SHARD_WEIGHTS` set to the measured part sizes, because a count split is not balanced in time. Each job restores an npm cache keyed on `package-lock.json` and runs `npm ci --prefer-offline`. Each shard writes a blob report, and a layout shard also uploads its `.layout-shards/` files. The job `visual` keeps the required check name. It fails when a shard did not succeed. It downloads the layout files and runs `layout-setup` with `KARST_LAYOUT_MERGE=1` (no web server): the ledger verdict judges the whole sweep once, and a missing layout file set fails it. It merges this blob with the shard blobs with `playwright merge-reports --config playwright.config.ts` into `.results.json` and `.report/`, and runs the gate. The gate also fails when the merged report lacks a test of the full listing (`VISUAL_LISTED_REPORT`). A merged report moves attachments into `resources/`, so the gate finds a failed baseline from the `Snapshot:` line of the error. Never run `layout-teardown` inside a shard: the ledger verdict must see every route. Local docker runs do not shard; they spread over workers (`@ui:WORKERS`).

**Theme filter before scheduling.** A test runs only in the projects that record it: `tests/visual/projectFilter.ts` gives each screenshot project a `testIgnore` for spec files of other projects and a `grepInvert` on the `@NOT-<PROJECT>` tag of `pages.visual.ts`. No test is listed and then skipped, so a shard does not pay for skips. Test titles, ids and baseline paths do not change.

**No karst UAT gate for `test:visual`.** The gate was intentionally omitted because `test:visual` always exits non-zero on macOS (container-authored baselines vs. macOS font rendering), and karst's gate system treats any non-zero exit as a failure — creating an unrecoverable loop. CI's `visual` job is the authoritative run.

**Fresh fixture pages.** `tests/visual/serve.mjs` clears and writes the pages at each start, for the views in `KARST_VISUAL_FIXTURE_VIEWS` (`@ui:FIXTURE-SCOPE`).
END_DOC_BLOCK: [@ui:RUNNING-SWEEP]

## [@ui:WORKERS] Worker count for the visual sweep

**Decision: the local docker gate runs `min(4, docker CPUs - 2)` workers, minimum 1, with `--fully-parallel`.** On the 6-CPU Docker VM that is 4. Two CPUs stay free for the Playwright runner, the fixture server and the VM. The host slot (`playwright-slot.lock`) lets one sweep run at a time, so two sweeps never share the VM CPUs. The agents on the host add load, so the cap stays at 4 and does not take all 6.

**The knob.** `scripts/dockerGate.mjs` reads the VM CPU count (`docker info`, 10 s limit) after it holds the slot, prints `visual: <n> workers (...)`, and gives the count to the first container only (`scripts/gateWorkers.mjs`). An explicit `KARST_VISUAL_WORKERS` always wins; `KARST_VISUAL_WORKERS=1` gives the old behaviour. An unknown CPU count gives 1. Inside the container, `tests/visual/visualWorkers.ts` validates the value, and an invalid value gives 1.

**Always 1 worker:** CI (`CI` forces 1), every `--update-snapshots` run (the `:update` scripts pass no count), the sandbox `local` branch (no Docker CPU count), and the flake re-run and the base re-run (`rerunEnv`), so that a screenshot that failed under load gets a calm second try.

**Distribution.** `test:visual:ci` and `test:visual:screens:ci` pass `--fully-parallel`, so each test is its own unit and the screenshot projects spread over the workers. The `layout` project is `fullyParallel` already. No spec has `beforeAll`, serial mode or a worker-scoped fixture, so the flag changes only the order and the spread, not a result. The layout ledger is worker-safe: each test writes its own shard, and only the teardown writes the verdict.

**Adoption rule.** A new default needs a wall-time saving of 25% or more. Scoped A/B docker runs (1 worker against the new default, same scope, same branch) are enough evidence. The 9-run table is not necessary.

**Evidence.** The first measurement (1, 2 and 3 workers, by file, before `--fully-parallel`): `@issue:WORKERS-01`. The A/B runs of this default: `@issue:WORKERS-02`.

**A/B result:** 62% wall-time saving (dashboard scope, 1342 tests: 655 s at 1 worker, 252 s at 4 workers, 0 unexpected).
END_DOC_BLOCK: [@ui:WORKERS]

## [@ui:UPDATE-BASELINE] How to update a baseline

```bash
npm run test:visual:docker:update
```

Baselines are container-authored (`ui:RUNNING-SWEEP`), so the update runs in the pinned Playwright image. A bare `npm run test:visual:update` records whatever the developer's machine renders, which is not the environment CI compares against.

The commit MUST cite the rule id (UI-R35) and say what changed and why. A diff in `__baselines__/` without an accompanying source diff is a review red flag.

## [@ui:VISUAL-DEFECTS] Real visual defects found

The following were discovered during Task 8's baseline review and are reported, not fixed:

1. **G1**: `.k-dot` is one filled circle whose only per-state difference is `background`. The grayscale baseline shows five identical circles.
2. **G3**: `--k-success-fg` / `--k-danger-fg` resolve to `var(--vscode-editor-background)`, causing contrast failures on filled surfaces in at least one theme.
3. **gettingStarted contrast**: Headings and lede use foreground on sidebar background, falling below WCAG AA 4.5:1 in dark and hc themes.
4. **settings contrast**: Nav captions and help text fall below WCAG AA in light theme.
5. **G6**: The server-logs surface renders SGR-coloured log lines with VS Code's terminal ANSI palette; some hues (red on dark/hc, green and yellow on light) fall below WCAG AA against the editor background. Reported, not fixed — the palette belongs to the user's terminal theme.
