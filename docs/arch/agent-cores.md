## [@arch:AC-02] Ticket-context shaping lives ONCE in `src/context/ticketContext.ts`

Ticket-context shaping lives ONCE in `src/context/ticketContext.ts` (`buildTicketContext`/`renderTicketContext`): the launch seed (extension, in-process) AND the `karst context` CLI both render from it. `renderTicketContext` has three section modes — `all`, `narrative` (authored text only) and `facts` (structured operational facts only) — so a launch can route each half independently: the authored half rides the kickoff's first user message, the facts half rides the instruction layer. `buildSessionSeed` returns `{ instructions, kickoff }` (`agent/seed.ts`), and `composeResumeSeed`/`composeConflictSeed` return the same split (`agent/entrySeed.ts`). The generated `/karst:<id>` command embeds a `node <ext>/dist/cli/main.js context --db … --manifest …` prefix so a running (or foreign) session can re-pull fresh state on demand. The stage section shows the ticket's CURRENT stage row except at `fix`, where it shows the failed gate stage's evidence instead — and the "not an agent-advanced stage" advisory is driven by the ticket's actual current stage (`ctx.stageCurrent`), never that evidence row. The done-marker instruction itself is seeded ONLY when the marker exists: `markerStageFor` (`agent/markerStage.ts`) returns `MarkerStage | null`, and at `uat`/`review`/`ship`/`scope`/`done` the seed carries no marker at all — seeding `stage impl pass` there was a command the CLI refuses. When the marker IS the implementer's (`stage impl pass`), `renderDoneMarkerInstruction` appends one ask for an optional `karst notes post` learning (the project bulletin, v72) — derived from the command itself, so the live seed, `karst context`, and the generated `/karst:<id>` command all carry it while fix and gate surfaces never do. See `docs/arch/cli.md`, "`notes` / `notes post`".
END_DOC_BLOCK: [@arch:AC-02]

## [@arch:AC-03] Per-ticket launch model

Per-ticket launch model: `tickets.model` (nullable) overrides manifest `defaultModel`; `resolveModel` (`src/agent/models.ts`) is the precedence rule → adapter `--model`. The model list has exactly TWO copies and they must stay identical: `BUNDLED_CATALOG` (`agent/modelCatalog.ts`, the offline fallback, re-exported flat as `KNOWN_MODELS`) and the published feed `model-catalog.json` at the repo root (read by `modelCatalogLoader.ts` ONLY when a `feedUrl` is configured — precedence CLI → feed → cache → bundled). Adding a model means editing BOTH — `modelCatalog.test.ts` "matches the published model feed exactly" fails otherwise. The webviews render the host-supplied catalog (`state.models` / `refreshModelCatalog`), so there is NO model literal in any HTML. `discoverClaudeModels` is a deliberate stub: the Claude CLI exposes no model-list command. `discoverOpencode2Models` is NOT a stub: it runs the configured v2 launcher (`opencode2Command()` — the absolute `karst.opencode2.binaryPath`, never a PATH lookup, because v1 shares the `opencode` name) with `models --standalone` (the flag every v2 spawn needs; a bare `models` collides with the running managed service); an unset setting short-circuits to the benign `command-unavailable` state without ever spawning the `opencode2` sentinel. v2 prints the same `provider/model` lines v1 does, so both cores share `parseOpencodeModelList`. The CLI gives no effort vocabulary, so `loadModelCatalog` overlays the curated metadata of a matching bundled/feed entry onto every cli/feed/cache row by id — the human `label`, and `tags`/`efforts` when the row declares none — which is what keeps `#<effort>` working for the bundled opencode2 ids after a live discovery replaces the bundled list. Same shape for `tickets.type` (`store/ticketTypes.ts` → `{type}`): the ticket-form analyzer suggests one, but the host persists it ONLY while the ticket has none — an explicit pick is never overwritten. `TICKET_TYPES` and `CONVENTION_PRESETS` are mirrored into `settings/webview.html`; `webview.test.ts` pins both mirrors against the TS modules.

## [@arch:AC-04] A preset is a sparse capability → slot matrix layered over the manifest defaults

`agentPresets:` maps a name to `{ label?, slots: { <capability>: {provider, model, effort?} } }` — SPARSE, so an absent capability is Inherit. The eleven capabilities (`PRESET_CAPABILITIES`, `manifest/types.ts`) are the seven `processes:` keys (`uatTester`, `uatFix`, `review`, `reviewFix`, `prDescription`, `ticketAnalysis`, `planning`) plus `implementation` and the three graph profile ids (`graphExpert`, `graphWorker`, `graphFast` for approaches' `expert`/`worker`/`fast`; any other profile id is untouched). `activeAgentPreset:` names the preset applied to every ticket that names none of its own; `defaultAgentPreset:` is its deprecated alias — the two spell ONE active preset, so a file carrying both is refused at load rather than letting one win. `resolvePresetSlot` (`agent/agentPresets.ts`) is the ONE reader of the preset map: it answers "does the effective preset override this capability?" with a whole slot or `undefined`, where the effective name is the calling scope's own reference — `processes.<key>.preset` (deprecated, still read for one release with a load warning) → the ticket's `agentPreset` → `activeAgentPreset` → the `defaultAgentPreset` alias — and a blank or dangling name degrades to Inherit. Preset lookup is own-property only (`Object.prototype.hasOwnProperty.call`, never `in`), because a name like `toString` must not resolve to an inherited member.

Per-capability precedence, most specific first: the ticket's own provider/model/effort → the PIN (`processes.<key>` with `pinned: true`, "same in all presets") → the active preset slot → the legacy `agentProvider`/`defaultModel`/`defaultEffort` (graph slots fall back to `approaches[].graph.profiles.<id>`; a `processes.<key>` with `enabled: false` short-circuits to "absent" before any rung is read). **A slot is an ATOMIC (core, model, effort) triple**: it contributes only while the resolved core is the slot's own core, so an explicitly chosen different core drops the WHOLE slot — never just its model — and a model never crosses to another core (a pin is atomic the same way, and while it is live it shadows the slot entirely); without that gate a catalog-unknown preset model (a preview/custom id) would be accepted by the compatibility guard for ANY provider and launch on the wrong core. The caller that wants the pure settings defaults omits `explicitProvider` (the ticket form's Inherit label); `resolvePresetDefaults` composes slot-over-manifest-defaults for every launch path with no process config of its own (ticket launch identity, ship stage, the dashboard/sidebar/diagnostics views), `resolveProcessAssignment` composes it per role, and `resolveGraphNodeProfile` maps `expert`/`worker`/`fast` to the three graph slots, falling back to the approach config. Models on the ticket/slot/manifest rungs are catalog-gated (a pinned model stays verbatim on the core it declares) and an effort rides only when the resolved model advertises it — otherwise it is dropped, never silently launched (`resolveEffortForProvider`). Presets move provider/model/effort ONLY: the profile (`agent`/`agentName`) a row points at is the prompt source and is never touched by a preset. Back-compat: a legacy flat `{provider, model, effort?}` preset normalizes at load to the same slot on EVERY capability (≤ 50 presets), `processes.<key>.preset` is still read for one release but the writer drops it and no Settings row offers it, a dangling manifest-level reference is refused at load while a dangling `tickets.agent_preset` degrades to "no preset" (shown as unknown in the ticket form), and a manifest with no presets resolves byte-identically to the pre-preset defaults. Both resolvers return a `source` (`ticket`/`pin`/`preset`/`default`/`fallback`) beside the identity — the Agents page renders it as the row chip, so the layer that supplied a value is never hidden. An UNPINNED `processes.<key>` row carries only `agent` and `enabled`; core/model/effort on it are a validation error and legacy rows are folded into presets on load (`docs/arch/manifest-and-settings.md` `arch:PIN`). The Agents page owns the vocabulary and the matrix (see `docs/arch/manifest-and-settings.md`); worked Cheap/Free/Smart presets are commented into `karst.example.yml`.

## [@arch:AC-05] A missing optional provider CLI is a normal state, not a fault

The model catalog resolves per provider through cli→feed→cache→bundled, and every tier that declines files a `CatalogDiagnostic`. `catalogDiagnosticSeverity` (`agent/modelCatalogLoader.ts`) is the ONLY thing that decides a log level: `command-unavailable`/`unsupported`/`empty` are INFO (the next tier covers them), everything else is WARN. The category is carried, never re-derived — `DiscoveryResult` now returns a `code` because `classifyCliFailure` used to substring-match the human-readable `reason`. `reason` is unbounded CLI prose and must never reach a log line; `target`/`cause` are the bounded exception and are re-validated inside `formatCatalogDiagnostic`. **The feed tier is opt-in with NO default URL.** `model-catalog.json` at the repo root is the publishable artifact (pinned by `modelCatalog.test.ts`), not something anything fetches by default.
END_DOC_BLOCK: [@arch:AC-05]

## [@arch:AC-06] A failed headless CLI run is described in ONE place for every agent core

`agent/cliFailure.ts` (`describeHeadlessFailure`/`isUsageLimitFailure`) is what each adapter's `runHeadless` throws. It unwraps whole-document JSON AND JSONL (the interesting codex event is never line 1), names a usage limit from a 429 status / limit phrasing, and keeps raw text ONLY when nothing structured parsed — an unrecognized failure must stay debuggable. Every diagnostic is untrusted CLI prose (it can be model output), so it is collapsed to one line and capped before reaching a verdict, a log, or a toast. The bare-429 match uses lookarounds on purpose: `src/foo.ts:429:12` must not send the user to a billing page.
A run the spawner KILLS (a timeout, T663) rejects with `error.name === 'TimeoutError'` (matched by `failureClass.isTimedOutFailure`, which `classifyFailure` also uses) and carries the counts `extractTokenUsage` can still read from the partial stdout via `attachUsage` — so the meter records what the runaway really burned instead of an estimate from the prompt, and the UAT Tester's fresh-token budget can see it. The raw partial stdout rides on the error too (`capturedStdoutFromError`, non-enumerable), so a core whose counts the generic scan cannot read parses its own: opencode2 reads its nested `part.tokens` with `parseOpencode2JsonlUsage` and attaches that.

Antigravity has one failure that is NOT a non-zero exit: headless `agy -p` cannot prompt, so a tool needing approval is auto-denied and the run exits 0 with only a `jetski: no output produced — a tool required the "command" permission that headless mode cannot prompt for…` notice. `describePermissionDenial` recognizes it and `runHeadless` throws it, so the review findings lane and UAT tester report the named permission and the fix instead of "unreadable output". That sentence is persisted on the process run (`process_runs.failure_detail`, v81) and rendered as the Tester/Review process detail, with the `karst doctor` pointer appended for a denial (`isPermissionDenialDetail`), so a legacy run with no detail keeps its generic wording. Only agy needs this (codex `exec` has a read-only sandbox, claude keeps Read/Grep — AC-08 declared reason). agy's allow-rules live ONLY in the user's global `~/.gemini/antigravity-cli/settings.json`, which karst never writes (AC-17); `karst doctor` (`tools.agy-permissions`) reports which read-only commands are missing and the lines to add. **agy 1.3.3 matching rule, verified on the real CLI (`agy -p` in a scratch repo, minimal `permissions.allow`) and NOT inferred: a `command(<target>)` rule allows a shell command iff the command's whitespace-delimited TOKENS begin with exactly the rule's tokens.** `command(git diff)` covers `git diff origin/<base>...<branch>`; `command(git rev-parse)` does NOT cover `git -C <path> rev-parse --abbrev-ref HEAD` (the flag is the SECOND token — the `-C` denial that started this); `*` is NOT a wildcard — `command(git *)` requires a literal `*` token and matches nothing the lanes emit (the false-OK `[ok] tools.agy-permissions` the old prefix-wildcard assumption produced); `command(git)` is the broad form covering every git shape. `src/doctor/agyPermissionChecks.ts` mirrors this rule, and it probes the exact command shapes the scope block emits (`SCOPE_GIT_COMMANDS`, `workflow/agentScope.ts`) — not a hand-maintained list that drifts from the prompts.

## [@arch:AC-07] A SILENT run is an empty answer, never a failure

A core that exits 0 having emitted no assistant text answered EMPTY — `runHeadless` returns `raw: ''` and every adapter agrees on that. opencode and codex used to THROW here (`did not contain agent text` / `did not contain a completed agent message`) while claude and agy already returned `''`, so the same silence was a crash on two cores and an empty answer on the other two. It is a real shape, not a broken stream: opencode routinely ends a turn on a tool call, and a three-minute UAT run that did the whole job and never wrote the answer down reached `uat/tester.ts` as `execution-failed` — which abandoned every remaining target, recorded ZERO observations, and left UAT to pass on its gates with nothing but a debug line to say the Tester never ran. A stream missing its SESSION ID (`thread.started`, opencode's `sessionID`) stays a hard failure — that is a broken stream, not a quiet model. **The caller decides what silence means**: the UAT Tester re-asks the target ONCE with `TESTER_SILENCE_NUDGE` appended to the same prompt (context and output rules intact) and then records `unreadable-output`; unreadable PROSE is never re-asked, because the core did answer and a second ask buys a second helping of prose. Every other headless call site already tolerates an empty answer through its own parse fallback.
END_DOC_BLOCK: [@arch:AC-07]

## [@arch:AC-08] A FIX TO ONE AGENT CORE IS A FIX TO THE SEAM — all four adapters in the same commit, or a declared reason

A change that is NOT a translation of one CLI's own flag vocabulary lands on every adapter at once. Where a core genuinely cannot do it, that is DECLARED, never silently dropped — `agent/surfaces.ts` gives every adapter an `AdapterSurfaces` with a position on each optional field of the seam (`model`, `effortHeadless`/`effortInteractive`, `allowedTools`, `permissionMode`, `resume`, `sessionName`, `consoleStream`, `hookChannel`, `endpointRebind`, `mcpIsolationHeadless`, `readOnlyInteractive`, `addDirsInteractive`, `mcpConfigInteractive`, `processKillDeny`, `sandboxInteractive`), and `unsupported(reason)` REQUIRES the reason. `agent/adapterConformance.test.ts` is the enforcement: it loops `IMPLEMENTED_PROVIDERS` through `resolveAdapter` and checks each declaration against REAL argv (a claim is never taken on trust), plus the universal rules — bounded single-line failure text, `AbortError` from the shared spawner, `materializeApproach` never claiming a pre-existing repository dir, and every `ownedPaths` entry covered by a `KARST_EXCLUDE_RULES` pattern. So a fifth core is under test the moment it joins `FACTORIES`, and adding a field to `AdapterSurfaces` is deliberately a compile error in all four adapters. Rationale for shared behavior belongs at the SEAM (`adapter.ts`, the shared helper). Lifecycle signals have their own baseline: `docs/agent-cores/HOOK-CONTRACT.md` states what karst's needs-you / launch-intent / resume features require, and a core may satisfy it natively, by synthesis, or by WATCHING its own state (agy's conversation DB) — but never by a channel that looks installed and delivers nothing. `writeCurrentEndpoint` writes the endpoint file for every member of `BRIDGE_PROVIDERS`.

`mcpIsolationHeadless` has one verified argument per core, and the arguments are not interchangeable: claude passes `--strict-mcp-config` **alone** — pairing it with `--mcp-config '{}'` makes the CLI exit with `Invalid MCP configuration: mcpServers: Invalid input` before it does any work, because that value is schema-validated and requires an `mcpServers` key (this shipped once and turned every headless claude run into `execution-failed`); codex passes `--config mcp_servers={}`; opencode passes `--pure`; antigravity has no per-invocation flag at all and declares `unsupported(...)`. Presence of the right flag is not sufficient — `adapterConformance.test.ts` also holds `FORBIDDEN_HEADLESS_ARGS`, the arguments each core's CLI rejects, because a presence-only assertion cannot catch an extra argument.

`mcpConfigInteractive` is the interaction-time counterpart: claude (`--mcp-config <scratch file>`), opencode and opencode2 (the `mcp` section in the per-launch `OPENCODE_CONFIG_CONTENT`, verified on opencode 1.18.35) and codex (one `--config mcp_servers.karst.*` pair per TOML key, from `codexMcpConfigArgs`) declare it supported; only antigravity declares `unsupported(...)` and its agent registers the server with `karst mcp install` instead. The config file is written by the session launch into the extension's global storage — never a repo `.mcp.json` — and headless runs stay isolated (`mcpIsolationHeadless`), so the karst tools appear only in an interactive session, where the agent can use them.

`processKillDeny` is the process-wide kill guard (incident 2026-10-12: a UAT Tester ran `pkill -f claude` and SIGTERMed every live karst session on the machine). `agent/processKillGuard.ts` holds the ONE list (`pkill *`, `killall *`, `kill -9 -1`, `kill -1`, `kill -- -1`, `kill 0`) and the per-core translations; `kill <pid>` / `kill $!` stay allowed, and the deny is a best-effort pattern, not a security boundary (the prompt rule is the backstop for spellings it cannot enumerate). claude carries the deny in its `--settings` `permissions.deny` on a hook-channel launch, and in `--disallowedTools` on the read-only, headless, and hook-channel-less (graph node/planner) paths; opencode and opencode2 carry it in the shared `opencodeLaunchPermission` `bash` object (v1 `OPENCODE_PERMISSION` env, v2 `OPENCODE_CONFIG_CONTENT` `permission`), always — a `deny` survives `--auto`. codex and antigravity declare `unsupported(...)`: codex's execpolicy rules live in user/config-layer `rules/` files karst may not own (AC-17) and headless `exec` has no approval channel; agy's allow-rules live only in the user-global `~/.gemini/antigravity-cli/settings.json`. A prompt rule (`PROCESS_KILL_RULE`) states the correct way on the UAT Tester prompt, the fix brief and the resident impl/fix instruction layer.

The seam also has one ENVIRONMENT obligation, and it lands on opencode2 alone: `opencode2IsolationEnv` redirects `XDG_*` into karst storage, so it must also disable the OTHER CLIs an isolated run might spawn itself — `DISABLE_AUTOUPDATER=1` (Claude Code's documented switch, beside `OPENCODE_DISABLE_AUTOUPDATE`). Without it, a tester that runs the real `claude` from the isolated shell inherits the karst `XDG_DATA_HOME`, Claude's native installer copies itself under karst storage and relinks the user's global `~/.local/bin/claude` at that copy, and cleaning karst storage then breaks `claude` machine-wide (`doctor` `tools.claude-install` is the report-only detector; it inspects every candidate `claude` — including a DANGLING link cleanup leaves behind — and flags any that resolves into an `opencode2/data` dir of ANY karst install, not only this doctor's own storage). This is NOT a change to the `AdapterSurfaces` seam and needs no sibling work: opencode2 is the only core karst spawns with an `isolationEnv` that REDIRECTS its state directories (`XDG_*`) into karst storage — opencode v1's headless `isolationEnv` carries only the `OPENCODE_PERMISSION` overlay, and claude, codex and agy spawn under the host's own `HOME`/XDG with only `KARST_*` keys layered on — so no other adapter has a karst-owned data dir an updater could resolve into.

An oversized kickoff has ONE argv backstop on the seam — see AC-41.

## [@arch:AC-41] An oversized kickoff spills to a file — one argv backstop on the seam

The kickoff has ONE argv backstop on the seam (`agent/kickoffSpill.ts`, T722/D151): a kickoff whose UTF-8 length exceeds `KICKOFF_ARGV_MAX_BYTES` (100 KiB; Linux `MAX_ARG_STRLEN` is 128 KiB) is written in full to `<runtimeDir>/kickoff/karst-kickoff-<launch>-<rand>.md` and replaced by the short positional pointer `Your full kickoff brief is in <path>; read it completely before doing anything else.` The runtime dir is `cwd/.karst/kickoff` on the host and the mounted bridge dir in a sandbox (the pointer names `runDir`, never the host path); the file is a fresh name per launch, and only a worktree-local file is returned as an `ownedPath` (`/.karst/kickoff/` is an `OWNED_PREFIXES` entry). Every core's interactive path applies it — claude after `--`, codex after `--`/the resume id, opencode and opencode2 on `--prompt`, agy on `-i`. Opencode's RESUME path is the declared exception: it already writes the kickoff to a JSON file named by `KARST_KICKOFF_FILE`, so it cannot carry an oversized argv entry and does not spill twice. A kickoff at or under the threshold is returned byte-for-byte unchanged (same argv, same prompt hash, same cache). This is a positional/prompt guard, NOT the instruction layer: the body never moves into the kickoff file (`AC-09`).
END_DOC_BLOCK: [@arch:AC-41]

## [@arch:AC-09] The instruction layer rides each core's OWN system/developer channel, never the first user message

Karst's standing rules are one body, written to `<sessionDir>/karst-instructions.md` and exported to the child as `KARST_INSTRUCTIONS` (`agent/instructions.ts`, `agent/cliEnv.ts`). Each adapter DECLARES how it delivers that layer per launch path — `AgentAdapter.instructions` (`agent/adapter.ts`), an `InstructionDelivery { interactive, headless, acp }` whose values are `native-file` (the core's own system/developer channel reads the written file), `pointer` (a one-line kickoff/developer pointer names `$KARST_INSTRUCTIONS` and the body stays on disk), `fallback` (a solo-agent launch keeps the rules in the kickoff alongside the persona), or `n/a` (not wired yet). The BODY never rides argv as text; the conformance suite asserts the declared channel against real argv, that resume re-attaches the layer without duplicating the kickoff, and that no core inlines the body.

- **claude — `native-file`:** `--append-system-prompt-file <file>`, before the `--` positional and on `--resume` (verified present in 2.1.291). On a RESUME it adds `--system-prompt-snapshot off` — claude's default snapshot records the first request's system prompt and REPLAYS it verbatim on every later request and resume, so without the opt-out a resume would ignore the file karst just regenerated (`off` renders fresh and overrides the record). A fresh launch keeps the default `on`, recording the current file as the stable, cache-friendly prompt.
- **opencode — `pointer`:** a generated custom agent's prompt REPLACES opencode's base system prompt (verified on 1.18.32: `LLMRequestPrep` selects `agent.prompt` INSTEAD of the provider prompt), so no `--agent` is materialized; the kickoff opens with the pointer, after any leading slash command.
- **opencode2 — `pointer`:** v2 IGNORES the config `instructions` key (verified on 2.0.24), and `AGENTS.md` is rejected (it works, but pollutes the repo, collides with user files and can be committed by accident), so the pointer rides the TUI `--prompt` kickoff, after any leading slash command — the body stays on disk at `$KARST_INSTRUCTIONS`. If a later v2 honours the config key, upgrade to `native-file`.
- **codex — `pointer`:** `-c developer_instructions=<pointer>` (a developer-role message), placed before the positional resume id. `model_instructions_file` is NOT used: it OVERRIDES the model's sanctioned base instructions ("strongly discouraged" per codex config).
- **agy — `pointer`:** 1.3.0 has no instructions flag; the kickoff (`-i`) opens with the pointer.
- **headless/ACP** are DECLARED (`headless: 'n/a'`, `acp: 'n/a'`) with no behaviour change; the conformance suite makes any later wiring drift visible.
- **solo-agent launches on codex/opencode/opencode2** report `fallback` and leave the rules in the kickoff — the native channel cannot coexist with the materialized persona. The seam DECLARES this with `InstructionDelivery.soloFallback` (codex/opencode/opencode2 set it); the seed composer reads it and inlines the whole instruction body into the kickoff rather than writing a file (a fresh launch with no materialized entry command does the same — the self-contained fallback invariant).
- The pointer goes AFTER a leading slash command (`/karst:…`), NEVER before it (`withInstructionsPointer`). `measureSeed` (`agent/seed.ts`) measures both layers. A TICKET session records the seed (`seedChars` = kickoff + instruction body, `guidePointer`) and — when an instruction layer rides the launch — the instructions' size, stable digest and pointer flag onto the launch's `process_runs` row (`prompt_telemetry`). A PLANNING session has no run row, so its launcher measures the same layer through `planningOps.ts` and logs size + digest + channel at debug level only, never the body.

TICKET sessions (`extension.ts`) split the launch — `agent/seed.ts`'s `buildSessionSeed` returns `{ instructions, kickoff }`. The instruction body is the karst-authored rules and STRUCTURED FACTS — the `## Services` rule + resolved commands, the repositories in scope (paths, branches, worktrees, ports), the PR numbers/URLs, the guide pointer (fresh launches only) and the done-marker instruction — all via `$KARST_*` env refs. The kickoff is the workflow invocation FIRST, then the human/agent-authored text (ticket prompt/brief, parent summaries, mailbox pointer) and the approach method prompt. `renderTicketContext`'s `facts` mode supplies the structured half; `narrative` supplies the authored half. The file is written under global storage (`<globalStorage>/session-instructions/<id>/karst-instructions.md`), never into the tree. On a RESUME/conflict the instruction layer is REGENERATED and re-attached while the kickoff shrinks to the short continue/conflict message under the invocation (no rule repetition); the guide pointer is deliberately omitted from a resume's regenerated body, so the guide-pull denominator stays a fresh-launch measure. `extension/ops/planningOps.ts` is the other consumer: `planning/preamble.ts` splits into `planningInstructions` written to the file and an empty `planningKickoff`. Instructions are RE-WRITTEN from the running karst version on every launch, fresh or reopen.

## [@arch:AC-10] A planning launch uses each core's VERIFIED no-edit mechanism, never its native plan mode (agy excepted, declared unsupported)

`InteractiveCommandOpts.readOnly` (+ `addDirs`) launches a planning session (`extension/ops/planningOps.ts`): edits blocked or approval-gated, the stack repos readable, and the karst CLI's `draft propose` (one file into the scratch cwd's outbox) still possible. No planning launch names the registry or the manifest (args or env; pinned in `adapterConformance.test.ts` and `planningOps.test.ts`). Native plan modes fail the last requirement: claude's `plan` refuses the filing command and leaving it makes the session writable; opencode's `plan` agent is overridden by a project `opencode.json` that allows everything. None of this is an absolute read-only guarantee — it is "edits blocked" or "writes need approval", per core:

**Which core/model a planning launch uses is its OWN resolution** (`agent/planningDefaults.ts`), not the ticket's: the active preset's `planning` slot → `processes.planning` (Settings → Agents, "Planner") → the IMPLEMENTATION resolution, so a project that has never configured a planner keeps launching exactly what it launched before. A `planning` preset slot / row changes it for NEW sessions only; a stored session keeps its own core/model. The core still has to pass the read-only rule below — `planningOps`'s `readOnlyInteractive`/`confirmUnsafeCore` check is unchanged, and the model picker only offers the chosen core's catalog entries.

- **claude:** `--permission-mode default --disallowedTools Edit Write NotebookEdit`. Edit tools are denied; every other shell command asks. `default` overrides a saved acceptEdits/bypass mode.
- **codex:** `--sandbox workspace-write` + `writable_roots=[]`. The cwd is a karst scratch dir (`<globalStorage>/planning-scratch/<id>`, never a repo, a tree apart from `karst.db`), so ONLY it — and with it the outbox — is writable. No `--add-dir` under readOnly (it would make the repos writable); the sandbox reads the whole disk. There is no `writableDirs` option any more: nothing re-opens the registry dir.
- **opencode:** `OPENCODE_PERMISSION` env `{edit: deny, bash: {'*': 'ask', <kill deny>}, external_directory: {*: ask, <dir>/**: allow}}`. opencode merges it after every config file, so it wins; `addDirs` become `external_directory` allows (the TUI has no extra-dir flag). Verified via `opencode agent list`.
- **opencode2:** a singular `permission` object nested in `OPENCODE_CONFIG_CONTENT` — the SAME object v1 uses (`opencodeLaunchPermission` in `agent/opencode.ts`), carrying `{edit: deny, bash: {'*': 'ask', <kill deny>}}` for `readOnly` (the kill deny is always present) and `{external_directory: {*: ask, <dir>/**: allow}}` per add-dir. v2 IGNORES the v1 `OPENCODE_PERMISSION` env and the ordered `permissions` array is the resolved internal shape, not an input; it appends CONFIG_CONTENT rules after a project `opencode.json`, and last-match-wins, so the ruleset wins. Live-verified on 2.0.24: `edit` deny refuses a file edit, so `readOnlyInteractive`/`addDirsInteractive` are declared SUPPORTED and a planning launch needs no `confirmUnsafeCore` acknowledgement. Headless `bypassPermissions` is REFUSED (`arch:AC-31`): `--auto` is never passed, because no enforced sandbox contains the run.
- **agy: `readOnlyInteractive` is DECLARED `unsupported`.** agy 1.2.17's `--mode` accepts only `accept-edits` | `plan` (`agy --help`); any other value (the earlier `default`) is rejected and agy falls back to its SAVED mode — possibly `accept-edits`, i.e. silent edits. A readOnly launch therefore passes `--mode plan`, the only non-editing mode, which also overrides a saved `accept-edits`. agy has no deny list and no ask-everything mode; `--sandbox` only restricts the terminal, not file edits. Plan mode "researches without making changes", is not verified as an enforced boundary, and may refuse or ask before the `draft propose` command. Not live-verified (quota). Because it cannot block edits, `planningOps` calls the injected `confirmUnsafeCore` before EVERY launch on a core whose `readOnlyInteractive` is unsupported (`extension.ts` binds a modal: "agy cannot block edits; approve each action."); a decline (or no binding) launches nothing and a new session is dropped. The acknowledgement is debug-logged (`[planning]`). `antigravity.test.ts` pins the flag to agy's valid set.

`adapterConformance.test.ts` pins each mechanism and checks that an ordinary launch never carries the policy.

## [@arch:AC-13] Retry and model fallback

The seam carries TWO decorators and the order is load-bearing: `resilientAdapter(instrumentAdapter(adapter))` (K6). Each retried or fallback attempt passes through the meter on its own and lands its own `token_usage` row; the reverse order would report one row for N attempts and under-count a run that burned three of them.

`resilientAdapter` (`agent/resilientAdapter.ts`) wraps `runHeadless` only, delegating every other adapter surface verbatim. It classifies each thrown failure into one of five classes via `classifyFailure` (`agent/failureClass.ts`), which judges by MESSAGE TEXT (K1) — except quota exhaustion, whose typed `UsageLimitError` is also recognized by instance/name. Anything it does not recognise is `fatal`, so an unrecognised failure behaves exactly as it does today:

| class | source | behavior |
|---|---|---|
| `aborted` | `err.name === 'AbortError'` | rethrown at once — the user pressed Stop |
| `transient` | a bare 429 with NO quota wording, 5xx, network reset, "overloaded" | retried on the same model, `backoffMs` doubling, ±20% jitter, SILENT |
| `model-rejected` | a 400/404 naming the model, "unknown model" | no retry — the chain advances immediately, and the user is WARNED |
| `usage-limited` | a typed `UsageLimitError` (K11) | rethrown at once — no retry, no chain hop |
| `fatal` | 401/403, a timeout, anything unrecognized | rethrown at once |

**Quota exhaustion is user-resolved, never retried or hopped (K11).** A provider that reports the ACCOUNT is out of allowance (`quota exceeded`, `insufficient_quota`, `resource_exhausted`, `usage`/`spend limit`, …) cannot be helped by another attempt — retrying spends the same exhausted allowance (and, since fallback is off by default, usually the same model), and hopping runs a model the operator did not pick. `cliFailure.ts` names this subset `QUOTA_PHRASES` (narrower than `LIMIT_PHRASES`, which also matches the transient `rate limit`/`429`/`too many requests`/`limit reached` wording) and every adapter throws a typed `UsageLimitError { tool, provider, model, status, detail }` for it; `resilientAdapter` rethrows it at once. The class is read from the TYPED error, NEVER from message text. `isQuotaExhausted` reads only the provider's OWN error text — a structured ERROR envelope's message (stderr or stdout), else stderr — never an unstructured run's stdout (the model's answer), plus a structured quota `code` or HTTP 402. A BARE 429 with no allowance wording is still `transient`.

A TIMEOUT is deliberately not transient (K3): gate lanes run at `GATE_LANE_HEADLESS_TIMEOUT_MS` (60 minutes); retrying a timeout twice turns one lane into a three-hour lane.

**A model hop is user-visible and a same-model retry is not** (K9). A hop runs a model the operator did not pick and would otherwise make the token-usage stats unexplainable; toasting every 429 would train the user to dismiss the toast. The decorator emits structured facts (`ModelFallbackEvent`); the host writes the sentence (K10).

Interactive launches are NOT wrapped — only `runHeadless` carries the retry/fallback logic.

The chain always LEADS with the resolved model — a fallback never substitutes for the operator's choice — and fallback is off by default (`resilience.fallbackModels: []`). The `resilience` manifest block enforces bounds: 0–5 retries, 0–60 000 ms backoff, at most 5 fallback models. `resolveModelChain` (`agent/models.ts`) builds the chain, deduplicating and filtering by provider compatibility.
END_DOC_BLOCK: [@arch:AC-13]

## [@arch:AC-14] Token spend is measured ONCE, at the agent seam — never at a call site

`agent/instrumentedAdapter.ts` decorates `AgentAdapter`, so every AI invocation is counted by construction: `tracking: { callSite }` on its `runHeadless` opts, where `callSite` comes from the closed `AI_CALL_SITES` set (`agent/aiCallSites.ts`). A call that declares none is filed under `unknown` — visible, never dropped. `extension.ts` wraps at BOTH `resolveAdapter` sites; an un-instrumented one compiles and silently records nothing, so `ui/usage/wiring.test.ts` pins it. Three rules keep it safe to leave on: the store write is wrapped and swallowed (a locked DB must never fail a PR description), a FAILED call is still recorded (a 429 arrives after the input was billed), and an estimate is MARKED (`estimated`) and used only when the core reported nothing. Counts are parsed by one provider-agnostic reader (`agent/tokenUsage.ts`, whole-doc JSON + JSONL) which prefers a provider total, takes a CUMULATIVE tally as-is rather than summing it, and drops non-numeric/negative values. **No prompt or completion text is stored** — `token_usage` has no column that could hold it. Aggregation is five SQL GROUP BYs (`store/tokenUsage.ts`), never an in-memory rollup; `sort` is the one query field that cannot be bound, so `parseUsageQuery` (`store/tokenUsageQuery.ts`) narrows it to a key of a closed ORDER BY map and an invalid query returns a NAMED error rather than an empty table that would read as "you spent nothing". **Reasoning tokens are their own counter (v45), and CACHE READS ARE NOT THE HEADLINE.** opencode reports thinking tokens in a cumulative `tokens.reasoning` beside `output`; it is now `reasoning_tokens` on both usage tables, never folded INTO `output` for the same reason cache reads and writes stay disjoint. The reverse defect is `cache_read_tokens`, which was folded INTO the displayed total: a long opencode session re-reads its whole context every request, so 3.7M of a 3.9M tally was cache — the Σ pill and the usage panel reported 3.9M for a conversation whose own terminal showed 154.5K of context, which reads as a runaway agent rather than as ordinary prompt caching. **The stored `total_tokens` stays the provider-faithful full tally; the DISPLAY subtracts cache reads and shows them beside the headline** (`tokenView` in `model/inside/agent.ts`, `totalsView` in `ui/usage/state.ts`), clamped at zero because the two sums are independent and a legacy row can carry reads its total never counted. A terminal's own token figure is usually CONTEXT SIZE, not cumulative spend — the two are different quantities and are never reconciled.

## [@arch:AC-19] The seed-shape rule

A seed is the prompt text karst composes for a headless agent session. Whether a block of content goes inline in that seed or behind a CLI indirection is decided once, by audience:

- **A seed a HUMAN reads** (the interactive launch, its resume, its fix resume, the merge-conflict handoff) carries only narrative content inline and pulls operational facts through `/karst:start-task` → `karst context <key> --md`. The human must not be asked to scroll through worktree paths, branch names, service ports, or PR URLs to reach the sentence that tells them what to do next.
- **A seed only a MACHINE consumes** (the three graph-planner prompts) keeps everything inline, because indirection there buys no readability and adds a failure mode — the machine does not scroll, and a missing `karst context` call is a silent data loss.

The three standing counterexamples where inline is correct by this rule:
1. `launchPlannerRepairHost` — the G2 compile-repair re-prompt (`extension.ts`'s planner-repair host binding).
2. `launchReplanPlannerHost` — the replan planner launch (Slice-4 T5).
3. `launchBootstrapRelaunchHost` — the bootstrap planner relaunch after `planner-relaunch` recovery.

All three compose the prompt from `promptBytesOf('karst-graph-planner')` plus `renderTicketContext` directly, with `bounded: false` — the graph-planner prompt is a different surface from the interactive seed and never shares its bounds.

## [@arch:AC-27] An OpenCode v2 session warns before it opens with no provider signed in

## [@arch:AC-28] An opencode2 plugin's setup() never awaits a long-lived stream

Symptom (2.0.27): an interactive opencode2 session opens but never works — the log shows `loading plugin … karst-bridge.js`, then nothing until `GET /api/model → 503`, and no `provider.updated` ever fires. Cause: v2 awaits every plugin's `setup()` before provider/model init, and the generated bridge ran `for await (const e of ctx.event.subscribe())` inline, a stream that never ends. Headless runs return early on `KARST_OPENCODE_HEADLESS=1`, which is why gates and reviews were unaffected.

`renderOpencode2Bridge` (`agent/opencode2Bridge.ts`) now starts the loop in a detached `pump(ctx, directory)` and `setup()` returns at once. `subscribe()` is still called synchronously inside `pump`, so no early event is missed; `pump` wraps everything (including `subscribe()`) in try/catch so the detached promise can never reject. Rejected: a timeout/race around setup (still delays boot, depends on v2 internals), a v2 `effect` export (no live fixture of its lifecycle), dropping the plugin for interactive runs (loses all hooks). No migration: `writeOpencode2Bridge` rewrites a differing file on the next launch. Tests (`opencode2Bridge.integration.test.ts`): `resolves at once while the event stream never ends`, `delivers events that arrive after setup has resolved`, `swallows a rejecting stream and a throwing subscribe() without unhandled rejections`, plus the headless `never subscribes` case.

## [@arch:AC-30] Every launch in a karst-owned cwd PRE-TRUSTS it — claude and codex write their own record, the rest are explicit no-ops

The bug (T661): claude opens on its per-directory folder-trust dialog ("Do you trust the files in this folder?", default `No, exit`) in a fresh graph workspace, the session dies ~1.5s in with no transcript, and karst records `dead at reconcile` while Resume loops. Trust of a PARENT does not cover its children, so trusting `graph/dt` never helped — the per-directory record is the only lever.

`AgentAdapter.ensureWorkspaceTrusted(cwd, opts?)` is the seam; `agent/workspaceTrust.ts` owns the per-core record. claude merges `projects[<key>].hasTrustDialogAccepted = true` into `$CLAUDE_CONFIG_DIR/.claude.json` (else `~/.claude.json`); codex merges `[projects."<key>"] trust_level = "trusted"` into `$CODEX_HOME/config.toml` (else `~/.codex/config.toml`) — both env overrides are the CLIs' official ones, and both formats were verified against the installed CLIs. The KEY matters: claude 2.1.296 reads the trust record under the repository ROOT, not the launch cwd — a launch in a repo subdirectory records the repo root, and a linked worktree records the MAIN worktree root (`<main>/.git/worktrees/<n>` → `<main>`) — so `trustKeysFor` writes BOTH the realpath cwd and that root (found by walking up to `.git`, never a git child process); writing only the cwd left a monorepo subdirectory or a ticket worktree untrusted (T661 UAT medium). opencode, opencode2 and antigravity have no folder-trust prompt and implement an explicit no-op — AC-08 requires every adapter to ANSWER, and `adapterConformance.test.ts` fails a core that omits the method. The JSON merge preserves every other key and the existing project entry; the codex merge is TOML-aware (a header with inner whitespace or a trailing comment still counts, so it never writes a second table TOML would reject, and a `[`-leading array element is not mistaken for the next header), keeps a replaced `trust_level`'s trailing comment, and leaves every other line byte-for-byte intact. Both are idempotent (already-true skips the write), NEVER overwrite a file they cannot parse (log + continue — the launch-exit detection reports the real failure), follow a SYMLINKED config so a dotfiles target is not left stale, and preserve the file's own mode (a hardened 0600 config must not widen; a new one is 0600). The read-modify-write runs under an EXCLUSIVE cross-process lock (an atomically linked lock file, bounded wait, stale takeover by pid): a bare atomic rename prevents a corrupt file but not a LOST update — two launches trusting different workspaces used to drop one record each (T661 UAT medium), leaving that workspace on the dialog. The lock is claimed WITHOUT waiting when free (the common launch stays synchronous); when held, the wait is returned as a Promise the caller awaits — the wait is async (`await sleep`), never `Atomics.wait`, so it can never freeze the extension host (T661 review medium). A writer that still cannot take the lock within the bound skips the write and logs rather than racing.

Call sites, ONE per launch path: the supervised CLI transport (graph node fresh + relaunch/Resume, and the planner), `planningOps` (planning-scratch), `setupOps` (setup scratch), `session.openSession` (ticket worktree), and the instrumented seam's `runHeadless` (every headless run). REJECTED: a skip-the-dialog flag (none verified; `--dangerously-skip-permissions` changes permission semantics), trusting the parent `graph/dt`, and a user-run workaround script (it must be re-run per workspace).

## [@arch:AC-31] Autonomous permissions only inside an enforced sandbox

Rule (D164, T667): a session may run with relaxed or no permission prompts ONLY when an enforced sandbox contains it. When the requested sandbox cannot be enforced (core cannot sandbox, platform not supported, sandbox setup failed), the run FAILS CLOSED to today's prompted behaviour and diagnostics say why; there is no silent fallback to host + bypass.

Delivery, as sub-tasks of T667, in order:
1. **Provider-native sandbox** (ST1). Each core uses its OWN OS-level sandbox: Claude Code sandbox settings; Codex `--sandbox workspace-write` with an approval policy; opencode, opencode2 and agy are verified, else declared unsupported through the adapter seam (`arch:AC-08`). ST1 cuts prompts; it is not secret isolation. ## [@arch:AC-32] Sandbox backends — where a session runs (`agentBackends`)

The text is shown flattened, never parsed for actions; a session that outlives the window records nothing. Closing the terminal does NOT dispose the sandbox.
- **Clone source** (T703): sbx v0.48.0 refuses `--clone` from a linked git worktree, and every ticket is one. `<clone-dir>` is a karst-owned standalone clone of the ticket branch (`git clone --no-hardlinks --branch <branch> <worktree> .karst/sbx-clones/<n>`, `origin` removed; `sbx/sbxClone.ts`), built by `resolveBackend` before the terminal opens; a clone failure or a missing worktree branch resolves to `host (<reason>)`. sbx adds `sandbox-<n>` to that clone; sync fetches it there and relays the branch to the host worktree. `dispose` removes the clone.

Adapters still never emit a bypass flag.
- **Edits are not live**: the agent commits inside; the host reads them by bundling the branch inside the sandbox (see the stage-contract bullet below). `karst.sandbox.sync` (`ops/sandboxSyncOps.ts`) fetches and fast-forwards the ticket branch in the host worktree; a non-fast-forward is refused and reported, never forced. ## [@arch:AC-37] Sandbox lifecycle, recovery and multi-window (ST8)

Split out of `arch:AC-32`; the backend itself is defined there.

- **Lifecycle** (`ops/sandboxLifecycleOps.ts`, ST8). Identity is derived, never stored: `agent/sandboxInventory.ts` lists `sbx ls` + `docker ps -a` by this project's `karst-<hash8>-` prefix and parses names back to ticket/core; other projects' sandboxes are never returned, a failing listing is reported, never fatal. Terminal close → nothing; ticket `done` → sync, then `runner.stop` (never remove; a failed sync only warns, the clone survives the stop, and a good sync retries the ticket's pending marker, `arch:AC-34`); idle → the same sync + `runner.stop` via a 10-min sweep (`idleSweep`): running, owned, no open session, ticket untouched > `STUCK_IDLE_MINUTES` (120, the doctor stuck threshold); accepted marker → the HOST ends the session (`ops/sandboxSessionEnd.ts`): an accepted done marker of the current launch, then `session.idle` of that launch's bound session that stays idle `SESSION_END_SETTLE_MS` (10 s, any newer event cancels) → the same sync + `runner.stop`, which raises `session-closed`; idle without an accepted marker never ends a session (interactive turns), the agent core is never made to exit; archive → `removeSandboxGuarded` via `ArchiveOpsDeps.beforeArchive`, BEFORE the ticket/worktree archive: sync first; a refused/failed sync asks *Open sync diff / Remove anyway / Cancel* (dismiss = cancel → archive blocked). A ticket with no listed sandbox is a no-op. Remove happens only on archive, provider switch or explicit user action.
- **Recovery** (`runSandboxReconcile`, after the bridge sweep, only with `agentBackends` set): running → adopted on next open (preflight lists it, the runner reattaches by name, no duplicate); stopped → left, restarted by the next `sbx run`/open; missing (and its runner listed OK) → the ticket's `session_id` is dropped so the next open starts a fresh provider session. Orphans (this project's sandboxes with no live ticket) are logged on activation and reported by `karst doctor` (state area, async collection, only with `agentBackend`; `doctor/sandboxOrphanCheck.ts`, report-only) and removed only by the confirmed `karst.sandbox.cleanupOrphans`.
- **Provider switch**: changing a ticket's core drops its session id; the old core's sandbox (its name carries the core, so even claude → codex) is removed with the same guard first, and a blocked remove cancels the switch. `resumeDecision` already refuses a foreign id; this is the second lock.
- **Multi-window** (`arch:GLOBAL`): stop / remove / adopt / session-drop act only on tickets this window controls: it holds the session (`ownedSessionTickets`), or the ticket is in this window's project and no window runs its session (`agent_state` not `running`). A closed terminal therefore never blocks archive or idle stop.

## [@arch:AC-40] Sandbox dependency setup and its network window

Split out of `arch:AC-36`.

- **Dependency setup** (`agent/sandboxSetup.ts`, `ops/sandboxSetupOp.ts`): a repository's optional `sandbox.setup` runs INSIDE the sandbox clone via `runGate` (cwd = repo root), because a bundle clone has no main checkout to walk up to for node_modules. Fingerprint = sha256 over the PRESENT lockfiles (package-lock.json, pnpm-lock.yaml, yarn.lock; path-sorted) plus the setup text, computed in the sandbox (`node`, else `sha256sum`/`shasum`), so an agent's lockfile edit counts before any sync; only `{fingerprint, status: running|ok|failed|deferred, exitCode, at}` is recorded host-side in `<root>/state/<id>.setup.json`. Started in the BACKGROUND at launch/reattach and re-checked BEFORE every sandboxed gate list: ok + same fingerprint = run gates; changed or missing = run setup; an in-memory per-ticket lock makes a second caller wait, bounded by 15 min, never start a second setup; `running` state with no lock (previous host/crash) is stale past that age, then its children and itself are killed via its pid file (`/tmp/karst-setup.pid`, written first by the setup script; none = nothing to kill) and it is rerun once; a Stop mid-setup kills it likewise and drops the record, never `failed`. A failed setup (same fingerprint) or a timeout REFUSES the gate list (`sandbox dependencies not provisioned: <reason>` / `sandbox setup timed out after <n> min`): the driver returns `blocked`, no gate runs, so no verdict, transition or fix attempt, and the exit-127 capability park (`capabilityGap.ts`) is never reached; one notification each. Failed output: last 40 lines in `<bridge dir>/logs/setup.log` (advisory). No `sandbox.setup`, no step. Retry: automatic when the fingerprint changes, or palette `karst.sandbox.setup` (forgets the record, reruns now). Known gap: keyed by fingerprint only, so a sandbox recreated without `dispose` keeps a stale `ok` until a lockfile changes or the palette re-run. **Network window** (`SessionRunner.setupWindow`, `manifest/sandboxSetupHosts.ts`): the setup (and only it) runs with the repository's `sandbox.setupHosts` (default `registry.npmjs.org`, `github.com`, `objects.githubusercontent.com`; port 443; host or `*.suffix`) reachable, closed in a `finally` after a failed, timed-out or aborted setup too. sbx: `policy allow network --sandbox <name> <host>:443,...` then `policy rm` for EXACTLY the hosts the open added (a host already in `policy ls` is not recorded, so an overlapping baseline allow is never removed); per-sandbox, no recreate, so it may open mid-turn. docker: ALLOW is a create-time env of the proxy, so open and close RECREATE the proxy (`startProxySidecar` with a `karst.allow` label; the baseline proxy has none) and cut live connections: the window only opens with NO agent turn active (`agentState !== 'running'`). With a live turn the state is `deferred` and the setup waits, bounded; at the bound the gate list is refused `sandbox setup deferred: agent turn active` (the one notification). Hence a docker create-time background start is skipped (the first pre-gate check, agent idle, runs it); sbx starts at create. A failure whose output names a host (`ENOTFOUND <host>` etc.) says `blocked host <host>` in the reason. Alternative deferred: a runtime allow file read by the proxy (no recreate), revisit if recreate cuts cause real incidents.

## [@arch:AC-34] Sandbox evidence bridge — a sandbox reaches the host through one verified file

A sandboxed agent (sbx, docker) cannot POST to the host hook endpoint. Its only path back is one append-only file the host reads and VERIFIES. Code: `agent/bridge/*`, `agent/hookBridge.ts`, `hookBridgeFiles.ts`, `fileHookSettings.ts`, `extension/ops/bridgeWiring.ts`, `markerRunner.ts`.

- **Layout**: per-ticket host dir `<globalStorage-root>/events/<id>/` holds `events.ndjson` plus the agent scripts. Poller offsets live in `<root>/state/<id>.json`, OUTSIDE the mount, plus `<id>.setup.json` (`AC-36`). The events dir is mounted rw and is the ONLY extra mount: docker at `/karst-bridge/<id>`, sbx at the same absolute host path (sbx mounts extra PATH workspaces; same-path is ASSUMED, verify at manual F5). `SessionRunner.bridgeRunDir` gives the agent-visible path. Host files the agent's text names are mirrored in (`bridge/mirror.ts`, write-only, 2 MB cap): `attachments/` (re-synced per launch), `logs/` (gate logs, last 5). `sandboxTextTransform` rewrites paths and the spill pointer before `scrubHostCli`.
- **Transport**: `HookChannel.runDir` is the agent-visible script dir. The shared `bridge.cjs` gains a `file://` transport (the opencode/opencode2 plugins use it too; claude in file mode gets an inline `--settings`). `emit-marker.cjs` appends done markers and waits for the host's reply (below). Adapters compose command paths from `runDir ?? configDir`.
- **Line schema**: one JSON object per line, `{"v":1,"kind":"hook","payload":{...}}` or `{"v":1,"kind":"marker","stage":"impl"|"fix","seq":"<nonce>"}`, plus `ticket`. `seq` (`[A-Za-z0-9_-]{1,64}`) only names the reply file; a malformed one is ignored. Lines over 64 KiB are rejected.
- **Verifier accept rules** (`bridgeVerifier.ts`): the line names the poller's own ticket; a marker names a markable stage that is the ticket's CURRENT stage; a hook's `session_id` must equal the bound session id once one is captured; before that, any `session_id` is accepted. Payload fields are allowlisted; `cwd` and `launchId` are REBUILT by the host, never read from the line. `launchId` is the ticket's CURRENT launch at read time, so unread lines left by an older launch get the new generation. Anything else is dropped and logged `[bridge] ticket <id> dropped: <reason>`.
- **Poller hardening** (`bridgePoller.ts`): opens with `O_NOFOLLOW|O_NONBLOCK`, requires a regular file, handles truncation, keeps partial trailing lines for the next read. At most `MAX_LINES_PER_POLL` (500) lines per poll; the rest stay unconsumed for the next tick. Marker runs are queued and serialised per ticket (`markerFlow.ts`); none is dropped.
- **Markers** run the existing `karst stage <impl|fix> pass` CLI as an ASYNC child (`markerRunner.ts`, no `spawnSync`). The CLI's own work check (`assertMarkerHasWork`) refuses an empty marker. For a sandboxed ticket `ensureSandboxSynced` (`arch:AC-32`) runs first: commits live only in the sandbox clone (`arch:AC-32`/`AC-33`), so without it the guard sees HEAD = base and refuses (incident T700). A commit is NOT a done signal (zero or many are valid); the marker stays an explicit agent signal.
- **Reply channel** (`markerReply.ts`): for each marker line the host writes `<events dir>/results/<seq>.json` `{v:1,stage,ok,retrying,reason}` (temp + rename, atomic). It is advisory text for the agent: the host NEVER reads a result file back (agent-writable, untrusted) and the verifier still rebuilds every trusted field. File only, no network path. `emit-marker.cjs <events.ndjson> <impl|fix>` contract: (1) refuses with exit 1, writing no line, while `git status --porcelain` shows uncommitted changes ("commit your changes first"); (2) appends the line with a random `seq`; (3) waits up to `MARKER_WAIT_MS` (60 s) for the reply and prints it. Exit **0** = accepted, stage advanced; **1** = refused, the reason is printed and NOT retried (empty work, wrong stage: tell the user); **3** = queued, the host retries on its own (also the timeout outcome: no reply yet).
- **Failure handling** (`markerFlow.ts`): permanent refusals (CLI `cannot mark…`, a diverged branch) are replied and shown, never retried. Transient failures (sync error, sandbox stopped, CLI or DB error) are persisted per ticket in the host-only `<root>/state/<id>.marker.json` and retried on attach (boot sweep), after a successful stop-time sync and on a backoff timer (5 s, 15 s, 60 s, then every 5 min); cleared once the stage advanced or the CLI passed. Only the first failure notifies; a retry that fails again stays silent, and after `MARKER_MAX_RETRIES` (8) the marker is dropped with one final "gave up" notification (the agent can emit it again). Every failure logs at WARN and notifies `Karst: <ticket> <stage> done marker failed: <reason>`. A non-fast-forward (host branch diverged from the sandbox) is the only case that asks the user: an error notification with *Open sync diff*.
- **Lifecycle** (`bridgeRegistry.ts`, per-ticket serialized): `attach` (idempotent), `detach` (terminal close: poller stops, dir stays), `dispose` (dir and state removed; palette command `karst.sandbox.dispose`), `detachAll` on deactivate, `sweep` at boot: re-attaches only open tickets this window owns, and removes the dir of every closed ticket, whatever window owns it and even if its sandbox is still alive (its events are moot: markers for a non-current stage are rejected, hooks for a closed ticket carry no signal).
- **The bridge never carries a verdict.** It carries hook events into `dispatchHook` and done markers into the CLI; verdicts stay exit codes.
- **Residual risk**: a sandboxed agent can still emit a valid own-stage `impl` marker early, identical to today's host agent. `assertMarkerHasWork` and the gates remain the check.
- **Known gaps**: only attachments and gate logs are mirrored; no hook reply channel in a sandbox (the marker reply above is separate; mail falls back to the typed-pointer sweep, `core:HOOK-03`); no MCP tools in the sandbox; both runners assume a bare `node` on the sandbox PATH (hooks invoke bare `node`); ports, services and gates inside the sandbox: `arch:AC-32` (ST7).
