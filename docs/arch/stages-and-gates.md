## [@arch:STAGEMACH] Stage machine

Stage machine (`src/workflow/machine.ts` + `graph.ts`): verdict-keyed transitions.
`Verdict = {kind:'passed'} | {kind:'failed';reason?} | null`. null NEVER transitions;
missing edge THROWS. Deterministic verdicts only (exit codes, never agent self-report).

**`closed` is an operator exit, not a stage on the rail.** A ticket whose work was resolved OUTSIDE karst (a teammate did it by hand, an agent session ran without karst, the provider ticket was never used) cannot be verified, so it must not become `done`: `done` keeps meaning every PR merged (`arch:DONE`). `closed` is in the `StageKey` union (so every `Record<StageKey, …>` must handle it) and in `ALL_STAGE_KEYS`, but NOT in `STAGE_KEYS`: it is never seeded on a new ticket, never drawn as a stepper cell, and no `STAGE_GRAPH` edge leads to it (`STAGE_GRAPH.closed` is empty, so `isTerminal` holds). Its ONLY entry is `workflow/closeTicket.ts#closeTicket`, a human assertion that requires a non-blank reason (an optional ref is stored, never trusted) and writes the `closed` row through `setStage`; `reopenTicket` drops that row and returns the ticket to a running `impl`. The stages the ticket passed through stay as history. Closing is store-level cleanup only: it refuses while a non-finished sub-task is open (the archive rule; a done or closed child no longer gates its parent), releases any autostart claim (a closed sub-task never auto-starts), resets `agent_state` to `none`, and RETURNS a `CloseReport` (`openPrs`, `worktrees`, `runningServers`) instead of deleting anything: killing a live terminal, stopping servers and removing worktrees are host actions, and an open PR or unmerged commit is work a person may still want. A closed ticket claims no delivery: `karst stats` leaves it out of `cycleTime` and the `escapedDefects` denominator, while activity metrics (gate runs, merge probes, ship steps, token spend) keep counting it because that work really happened. **Which test to write:** `isFinishedStage(stage)` (`done` or `closed`) answers "does this ticket have no more work?" Agents must never reach this path unconfirmed (a human-only CLI verb / dashboard action; over MCP at most a proposal a human confirms, `arch:CLI-13`).

## [@arch:IMPLUAT] impl→uat is an explicit marker, never inferred from the Stop hook

impl→uat is explicit marker (`markImplementDone`), never inferred from Stop hook.
The marker is REFUSED while `tickets.agent_state = 'waiting'` — the agent asked
the user a question and is blocked on their input, so the stage is not done.
`cli/stage.ts`'s `assertMarkerNotWhileWaiting` is the choke point: the CLI is the
ONLY entry that ever fires a marker (impl and fix both), so the guard lives there.

The concrete marker command is rendered by `karst context` under
`## How this stage ends` (`cli/context.ts`'s `renderStageEnding`), resolved from
`markerStageFor(stageCurrent)` at read time rather than at session launch. A
session that moved impl→fix mid-run is told `stage fix pass` — the section
reflects the ticket's CURRENT stage, not the stage the session was launched
under. At gate stages (`uat`, `review`, `ship`, `scope`, `done`) where
`markerStageFor` returns null, the section is replaced by the gate-only
instruction (`renderGateOnlyInstruction`), which tells the agent there is no
marker to fire at that stage. This section is a re-read path — the seed's inline
marker remains the primary carrier.

## [@arch:DONE] DONE MEANS MERGED — an ENTRY CONDITION on `done`, never a stage of its own

The graph is `ship ─pass→ done`; a landing is not work karst performs. **`ship` is where the ticket waits**: it passes its own work, then holds, `status: 'passed'` with a `blocked_kind = 'awaiting-merge'` block naming the unmerged PRs, until every PR reads merged. `workflow/mergeGate.ts` is the whole decision and it is a READ over state karst already keeps current (`prs.status` via `prSync`, `merge_checks` via `mergeSync`) plus at most one `transition` — it never runs git, never calls gh, and never merges anything. **Any PR status that is not literally `merged` — including `unknown` — is UNMERGED**: a lookup that failed must never read as a landing. Two entry points, and the split is load-bearing: `resolveShipLanding` runs from ship's own tail and is entitled to trust `nothing-to-merge`, while `settleShipGate` additionally requires the `awaiting-merge` block to already be present — a ticket freshly parked at `ship` pending its FIRST confirm click has no PR yet and so also reads `nothing-to-merge`, and without that guard the sweep would walk it straight to `done`. `settleShipGate` is otherwise idempotent and a no-op unless the ticket is AT `ship`, because the landing is observed from three unrelated places: ship itself (nothing to merge), the per-repo Merge click (`mergePr.ts` → `completedTicket`), and the background PR sweep noticing a merge a teammate did on GitHub — the ONLY path that can see that one, which is why `settleShipGates` rides the sweep in `extension.ts` rather than being a dashboard concern. **`nothing-to-merge` is a genuine pass**, not an empty case: a ticket whose work produced no diff opens no PR (ship's `hasChangesFrom` path — probed BEFORE the commit step for a CLEAN worktree, so a repo the ticket never touched never enters the commit machinery at all, and after the commit for a dirty one, since the commit is what changes the answer; an unreachable remote falls back to the LOCAL base ref rather than reading as "assume changes", and a push whose remote ref already equals local HEAD is a `note`, not a re-push that spends the whole push budget) and has delivered everything it had; it is unreachable from a ship that FAILED to open a PR it needed, because that throws and parks at `ship`. **A PR that merged while ship waited for Confirm is not re-shipped** (`workflow/mergedNothingNew.ts`): when a repo has no live PR and its CURRENT PR is merged, `probeMergedNothingNew` re-probes that PR's head (`gh pr view --json headRefOid`, `arch:GH-03`) and treats the repo as landed if the branch HEAD equals it or `git diff --quiet <mergedHead> HEAD` is empty — compared against the merged head, never the base, because a squash merge plus other landed PRs makes the base tree always differ. Ship then skips push and PR for it (note `already merged in #N — nothing new`), so an all-landed ticket passes to `done`; new work after the merge still opens a fresh PR. `settleMergedNothingNew` applies the same check in the PR sweep to a ship slot with no `awaiting-merge` block (clean worktrees only), and the ship preview shows `already-merged`. An unreadable probe answers not-landed. The provider status push fires from whichever path actually reached `done`, once (`pushDoneStatus`, window-scoped so no dashboard need be open); the manifest keys keep their `advanceOnShip`/`shipStatus` names for compatibility. At the `done` transition, `stopServersOnDone` (manifest root field, tri-state `ask` | `auto` | `off`, default `ask`) decides what happens to running services across the three done-entry paths (driver, onTicketCompleted, and the landed PR sweep, via `maybeStopServersOnDone`). `ask` prompts once with Stop servers / Keep running / Always stop (which writes `stopServersOnDone: auto`); `auto` stops without asking and announces; `off` leaves services running until archive. The outcome is recorded in `tickets.servers_on_done` (`asked` | `stopped` | `kept` | `auto` | `off`) to prevent re-prompting; rows remain offline and restartable without removing worktrees.
**`done` is not the only exit.** A ticket resolved outside karst ends `closed`, never `done` (`arch:STAGEMACH`); no landing was observed, so no merge claim is made and no done-entry side effect (provider status push, `stopServersOnDone`) runs for it.

## [@arch:BLOCKED] A ticket waiting to land is BLOCKED, not pending, and that is how a conflict reads `Needs you`

The wait is expressed with the block columns `stages` already has (`blocked_kind`/`blocked_reason`/`blocked_at`, `store/stageBlocks.ts`) rather than a second column set or a second stage. Five `BlockerKind` members do not mean "karst could not ask" — they are the USER-decided kinds: `awaiting-merge` (the question WAS asked — ship opened its PRs — and answered "not yet"), `awaiting-impl-marker` (the graph finished and waits for the marker), `baseline-review` (UAT's gates passed and changed visual baselines wait for the user's Approve/Reject, @arch:BASELINE-REVIEW), `tester-skipped` (the Tester observed nothing and `uat.testerObservations.onSkip` is `reask-then-park`, @arch:UAT-OBS), and `push-diverged` (ship's push was rejected non-fast-forward and origin holds foreign commits; the user picks Overwrite remote or Integrate via Fix push, @arch:GH-08). Resume refuses all five (`workflow/stageResume.ts`) and `needsUser` reads all five amber. `needsUser` (`model/ticketGlyph.ts`) reads it directly alongside the pending-confirm rule, so the ticket goes amber everywhere at once. The one yield: while an agent session is RUNNING (`agent_state='running'`), the needs-you reading pauses and the ticket reads in-progress — the block stays stored, so the reading returns the moment the session ends. No other needs-you source was added and none should be; a conflict is a *wording* difference, not a state one. `mergeGateState` separates `conflicted` from `awaiting` only so the UI can say "resolve this" instead of "click Merge"; the ship strip fails the row for the repo that cannot land. A conflict must NEVER be a `failed` verdict: `ship` has no `failed` edge, so it would park the ticket with no way out, and a retry cannot resolve a conflict — only a human rebase can. Both the gate and the strip read the CURRENT PR per repo (`listCurrentPrsByTicket`, `CURRENT_PR_ORDER`); a repo re-shipped after a merge holds both rows, and the stale merged one would answer for a branch still open. **The `awaiting-merge` block is the one block Resume may NOT clear** (`workflow/stageResume.ts`): every other `BlockerKind` means "karst could not ask the question, retry it", but this one means the question was asked and answered "not yet" — clearing it STRANDS the ticket, because `settleShipGate` needs exactly that block to tell "waiting to land" from "parked pending the first confirm click". The dashboard matches the refusal rather than offering a dead control: the blocked banner (`app/BlockedBanner.tsx`) renders NO banner for that kind at all. Ship's own tail keeps the pre-gate split: the landed path's `transition` is UNGUARDED (that is ship's verdict), while the not-landed block write is swallowed — the PRs are already open and the irreversible part succeeded, so bookkeeping over stored state must never turn a successful ship into a failed one. The parked row is stamped `endedAt` like any other passed stage; a passed row with a null `ended_at` reads as still running. Retiring a stage → move every ticket sitting in it somewhere valid in a migration (v25 walks `stage_current = 'merge'` back to `ship` with a placeholder block the next sweep re-checks for real); dead stage rows from a past migration are left in place, because a past migration is a record, not something to rewrite.
The same running-agent yield applies to a FAILED current stage (a stalled park a human re-opened a session on): while `agentState` is `running` the ticket reads in-progress (red → blue, no blocker chip, "In progress" label) via `ticketGlyph`/`agentWorkingOnFailedStage`; the stage row, its verdict and the rail history stay failed, and red returns when the session ends. `glyphFor` keeps failed > running for per-stage rails.

END_DOC_BLOCK: [@arch:BLOCKED]

## [@arch:RESULTS] Gate results and reported phases are append-only evidence

Gate results (`gate_runs`) and reported phases (`phase_marks`) are **append-only evidence** — `stages` is keyed `(ticket_id, stage_key)` and a retry overwrites it, so these are the only place a prior attempt survives. Both are written inside a transaction that commits with the stage outcome, whether that outcome is a verdict (`transition`'s `premutate`) or a block (`parkGateStage`, `store/stageBlocks.ts`) — `gate_runs` has two writers and both read `attempt` BEFORE any bump, so a run is filed under the attempt that ran. Surrogate `id` PK, deliberately: the natural key is not unique (a fail→fix→pass cycle files two invocations under one attempt), and `run_at` is what groups one invocation.
END_DOC_BLOCK: [@arch:RESULTS]

## [@arch:EVIDENCE-WHEN] Evidence is written WHEN IT HAPPENS, not when the run ends

A gate run used to collect every `gate_runs` row in memory and commit the lot inside `finish()`, so an extension-host restart mid-run discarded all of it and left the stage reading `running` from a timestamp belonging to a run that no longer existed. `stage_runs` (v25) exists only to resolve that ambiguity: `workflow/gates/evidence.ts`'s `openGateRun` opens a row BEFORE the first gate starts, and `uat.ts`/`review.ts` append to it the instant each piece of evidence is produced — **one `gate_runs` row per GATE as that gate finishes, appended from `runGateList`'s `onGateComplete`, never batched to the end of a target; and findings per TARGET as each lane call returns (`findingsLane.ts`'s `persistFindings`), before any aggregation rule reads them**. A host that dies mid-target-list or mid-lane keeps every gate that finished and every target that answered. `openStageRun` marks any still-`running` row of the same ticket+stage `stale` the moment it is SUPERSEDED — the driver single-flights per ticket, so a second open run can only mean the first one's host died — and the activation sweep (`reconcileStageRuns`, global like the server sweep) marks stale whatever a dead pid left behind; a row with NO pid, or one alive in another window, is left strictly alone. None of this loosens the VERDICT: it is still all-or-nothing, committed only by `commitGateOutcome`'s single transaction, and a throw there still leaves the ticket exactly where it was — only the EVIDENCE stopped being lost.
END_DOC_BLOCK: [@arch:EVIDENCE-WHEN]

## [@arch:GATE-OUTPUT] Gate output is a LIVE stream and a post-run artifact, and the artifact stays the record

A running gate is observable WHILE it runs: `runProcess`'s `onOutput` hands each decoded stdout/stderr chunk to `runGateList`'s `onGateOutput` (tagged with the gate's name), `uat.ts`/`review.ts` forward it, and `driveTicket.ts` tags it with the STAGE before the host's `GateConsole` (`workflow/gates/gateConsole.ts`) sanitizes it — the same `sanitizeAgentOutput` the agent lanes use, so untrusted CLI prose can never move the cursor, clear the screen or retitle the console — and posts it to an OPEN panel as `stage-output`. This mirrors the agent lanes (`AgentConsole`, the Tester and findings-lane consoles) with ONE deliberate difference: **`GateConsole` persists nothing.** The stage artifact, written by the existing recording path, remains the durable record, and the post-run console keeps reading exactly it through `stage-log` — the live stream only mirrors bytes that are still arriving. A stage console opened mid-run is therefore REFUSED by `stage-log` (no artifact is recorded yet) and the webview replaces that refusal with a live terminal the moment the first `stage-output` chunk lands; a chunk that races the answer is buffered, never written above the tail it belongs under.

**The console entries are offered WHILE the work runs, and a process's is independent of its stage's.** `ui/dashboard/state.ts`'s `consoleFor` flags a gate stage whose artifact exists OR whose stage is `running` — gating on the artifact alone hid the stage console for exactly the window the live stream exists to cover. The gate-lane AI processes (Tester, Review) carry their OWN `console` flag (`model/inside/gates.ts`, set as soon as a `process_runs` row exists, open or finished), and the webview renders that button from the process flag alone: a running Tester streams through `AgentConsole` before the stage has any artifact, so tying its button to the stage's availability made the live output unreachable for the whole run. Both refusals recover the same way — `agent-log`'s error sets the blurb, and the first `agent-output` chunk swaps it for a live terminal, exactly as `stage-output` does. The uat/review REPORTS carry the same entry: `ArtifactSummary.agentConsole` names the process whose console the report can open (`tester`/`review`, null when none ran), host-derived like every other availability (UI-R31).
**Base drift (D313).** When the container-pinned visual/layout sweep fails, `scripts/dockerGate.mjs` re-runs ONLY the failing screenshots (ids from `tests/visual/.results.json`) in a detached worktree of the merge base, inside the slot it already holds and with the same node_modules volume (`scripts/baseDrift.mjs` holds the pure logic). A screenshot that fails at the base too is *develop drift, not this ticket*: listed in the gate output with a `NOTICE: develop has N drifted screenshots` line, and it does not fail the gate. One that passes at the base is the ticket's break and fails as today. Never judged as drift: a baseline the ticket itself recorded (@arch:BASELINE-REVIEW), any non-screenshot failure, and more than 40 failing screenshots (`base likely drifted wholesale`). The temporary worktree is always removed.

**Base drift for command test gates (D360).** `test:unit` and `test:integration` run through `scripts/vitestGate.mjs` (pure logic in `scripts/vitestDrift.mjs`). When vitest fails, the failing ids (`FAIL <file> > <test>`) are re-run, file by file, in a detached worktree of the merge base (node_modules reused, worktree always removed). A test that fails at the base too is develop drift: listed with `NOTICE: develop is red: <ids>`, and if ALL failures are drift the gate exits 0. One that passes at the base is the ticket's break and fails as today. Verdicts are cached per (repo, base sha, test id) under the git common dir (`karst-base-red/<sha>/`), so concurrent tickets on one base re-run it once, and the first drift on a base sha prints one `KARST-ALERT: develop-red base=<sha> tests=<ids>` line (deduped per sha) for the host to raise as the project-level alert. Never drift: no parseable ids, more than 15 failing files (`base likely broken wholesale`), a test file the ticket changed.

## [@arch:GATE-SWITCH] A gate may be switched off for ONE ticket, and that is a filter over resolution's OUTPUT, never a change to resolution

`tickets.disabled_gates` (v24, JSON `{uat:[],review:[]}`, NULL = nothing disabled) is read at run time by `stages/uat.ts` and `stages/review.ts` and applied by `workflow/gates/disable.ts`'s `partitionDisabled` — `workflow/gates/resolve.ts` never sees it, so "what did the config declare or the repo offer" keeps exactly one answer. A disabled gate is still RECORDED: one `gate_runs` row with `skipped = 1` and no exit code, which is a different fact from `exit_code IS NULL` ("the repo defines no such script, NOT a pass") — `model/inside/gates.ts` renders the two as `skip` and `note`. Skipped rows never enter `entries`, so no aggregator can mistake one for a question that was asked. A stage whose every gate the user disabled is BYPASSED, never passed: `aggregateUat`/`aggregateReview` return the distinct `{ kind: 'bypassed' }` verdict (`model/types.ts`), the machine takes the forward (`passed`) edge so the pipeline continues, but the stage row records `status = 'bypassed'` — not a gate pass, because nothing was proven. The webview renders it with its own `⊘` glyph and `.seg.bypassed` rail class (`ui/dashboard/webview.html`), distinct from passed's green `✓`; the sidebar peek says "<stage> bypassed" and the Inside gates row reads `skip` with "all N gates disabled — stage bypassed". The store writer is per-stage (`setDisabledGates(store, id, stage, names)`) for the same reason Settings Save is per-tab. The dashboard's toggle list is the RESOLVED names, computed async host-side (`ui/dashboard/gateOptions.ts`) — the raw manifest list would offer a toggle for a gate that never runs, and omit one that does.
**Project-wide switch (T824).** A manifest gate may carry `enabled: false` (absent = on) in `uat.gates`, `review.gates` and the per-repository overrides. It reuses this same path: `applyConfigSwitch` (`workflow/gates/disable.ts`) names the config-off gates and `resolveTargetGates` / `resolveReviewGates` merge them with `tickets.disabled_gates` before `partitionDisabled`, so they leave `skipped = 1` rows. When EVERY declared gate is off, nothing runs and the stage bypasses; `uat.probeWhenAllDisabled` / `review.probeWhenAllDisabled: true` resolves as if the list were empty (package.json probe). An override whose gates are all off still replaces the global list. `enabled` is part of `gateRevision`. The dashboard per-ticket list shows config-off gates as `off in Settings` with no switch.

## [@arch:DISCOVERY] Auto-discovery is npm-shaped; gating is not, and the blocker must say so

`resolveGates` (`workflow/gates/resolve.ts`) returns declared gates **before it reads the probe at all** — so a repository whose gates are every one of them `kind: command` never touches `package.json`, and neither an absent nor a malformed one can block it. Only the ZERO-CONFIG path is Node-shaped: `probeScripts` reads `package.json` scripts, and a discovered gate is invoked as `npm run <script>`. That split is deliberate and is not a gap to close by teaching the probe other ecosystems — a `kind: command` gate is argv-based, spawned without a shell, and already expresses `pytest`, `cargo test`, `go test ./...` and `./gradlew test` exactly. **The defect was never the capability; it was that the `nothing-to-run` reason named only the npm path**, so a Python or Rust project read "karst is Node-only" and wrote a `package.json` whose scripts shimmed out to its real toolchain — the precise thing the command kind exists to make unnecessary. The reason therefore names the escape hatch, and distinguishes "no package.json at all" (the ordinary non-Node case) from "package.json defines none of the probed scripts" (a Node repo that is simply missing them); the Settings empty state and `karst.example.yml` carry the same sentence, because the moment the user needs it is the moment they are looking at an empty gate list. Guards: `gates/resolve.test.ts` "points a repo with no package.json at command gates", `ui/settings/webview.test.ts` "names command gates in the empty state".

A gate `command` carrying a path separator is resolved against the gate's `cwd` before the platform shim sees it (`runtime/commandCwd.ts`), so `.venv/bin/pytest` and `./gradlew` mean the worktree — a bare name stays a PATH lookup, because that is what `pytest` or `go` is asking for. On POSIX this only makes explicit what `execvp` already does after the child chdirs; on Windows it is load-bearing, since `resolveOnPath`'s existence check would otherwise run against the extension host's directory and fall through to an ENOENT.
A `kind: command` gate whose command is `npm|pnpm|yarn run [flags] <name>` gets that `<name>` derived as its `script` (`gates/npmScript.ts#deriveNpmScript`, `derivedScript: true`; `--if-present` derives nothing), so `runGateList`'s missing-script guard applies to it exactly as to a `kind: script` gate — `-s` would otherwise hide npm's "Missing script" behind an empty exit-1 body. A failing gate with an empty body gets `exited <n> with no output (command: …)` so the fix brief never carries a bare red.

## [@arch:GATE-CAPABILITY] A gate that could not RUN its command parks as capability-missing, never fails
covers: src/workflow/gates/capabilityGap.ts, src/workflow/uat/aggregate.ts#aggregateUat, src/workflow/review/aggregate.ts#gatesOutcomeBeforeFindings, scripts/dockerGate.mjs, scripts/nativeToolchain.mjs

Exit 127 is POSIX's "command not found": the binary a gate runs is not installed where the gate ran. A karst sandbox has no docker (it never mounts the docker socket) and no C++ toolchain, so a container-pinned visual gate and a native-addon rebuild both land there — the command was never RUN, so the gate has no verdict to give about the ticket's code. UAT and review therefore PARK (`capability-missing`, no fix attempt consumed) instead of recording a red the ticket cannot clear: the same line the dependency-drift check already draws ("a SETUP failure ... the caller parks"). The park replaces the verdict only when EVERY failed gate is a missing command — a gate that failed for an ordinary reason is the ticket's to fix, and a capability gap never swallows it. The park names the gates and quotes what each said about the missing command, and the repo's own scripts make that sentence actionable — `scripts/dockerGate.mjs` names docker and the repair, `scripts/rebuild-better-sqlite3.mjs` names the toolchain and the apt line — so the park reason is the fix, not a code to look up. The sandbox image carries the capabilities a repository's gates need (a C++ toolchain, and the pinned browser and fonts the visual baselines belong to), so a gate that CAN run in the sandbox runs in the sandbox; the marker `/opt/karst/visual-baseline-env` is what lets a local sweep stand in for the container, and only there — anywhere else a local sweep would answer a different question.
**A stale ticket branch parks the same way.** When a derived command-gate script is missing from the worktree's package.json, `runGateList` asks the BASE branch (`resolveTicketBaseRef`, `git show <base>:./package.json`). If the base defines it, the branch predates the script: the result carries `staleBranch` and UAT/review park `capability-missing` (no fix attempt consumed) with `gate "x" runs npm script "s", which <base> defines but this branch does not — rebase onto <base>`; the repair is the stage-menu "Rebase on base" (`rebaseOnBaseOps`). If the base lacks it too, it is an ordinary required-gate failure naming the script. Guards: `gates/runList.test.ts` stale/neither-defines cases, `uat/aggregate.test.ts` "aggregateUat — stale branch".
**A gate killed by memory pressure parks `resource-killed`, never fails.** Exit 137 (SIGKILL) with no failing-test marker in the output (`gates/resourceKill.ts#isResourceKill`) is an environment fault: the Docker VM is shared by every sandbox. A 137 beside a real failing test stays an ordinary failure. Per gate, `onResourceKill` (`retry-then-park` default | `park` | `host`) decides: `runGateList` reruns once as `env KARST_GATE_MAX_WORKERS=1 <cmd>` (the vitest configs read it), or reruns on the host process (`host`, same verified-sync path as `sandbox: host`). A gate still killed carries `resourceKilled`; UAT and review park `resource-killed` (no fix round, no recovery round), unless another gate failed for an ordinary reason. Guards: `gates/resourceKill.test.ts`, `gates/runList.resourceKill.test.ts`, `uat/aggregate.test.ts` "resource kill".
END_DOC_BLOCK: [@arch:GATE-CAPABILITY]

## [@arch:UAT-OBS] UAT Tester observations are advisory BY DEFAULT, and one knob makes them a verdict

The AI UAT Tester (`workflow/uat/tester.ts`) records OBSERVATIONS. They are evidence: `aggregateUat` never sees them — the pure gate aggregate stays free of AI output, and that does not change — so by default an observation can never pass, fail, transition, or spend a recovery round. Two things, and only two, can make the Tester decide UAT:

1. `uat.testerVerifier` — the deterministic boundary whose COMPLETED nonzero exit fails UAT (`tester-verifier-failure`).
2. `uat.testerObservations.blockingSeverity` — **the ONE knob that makes an observation itself a verdict.** Its default is `'none'`, and an absent `uat:` block, an absent `testerObservations:` block, and an absent `blockingSeverity:` all read as `'none'`: **every existing manifest keeps today's advisory behavior byte-identically.** Set to a severity, `runUatTester` counts the recorded observations at or above it (over the FINAL capped list, so a truncated observation never counts) and reports `blocking`; `stages/uat.ts` — never `aggregateUat` — turns a nonzero count into `{ kind: 'failed', reason: 'uat tester observations: 1 high' }` with a recovery round attributed to `sourceProcessId: 'tester'` (`triggerKind: 'blocking-tester-observations'`), exactly mirroring the verifier's failure path. The check runs AFTER the verifier, so the deterministic boundary keeps precedence.

The reason prefixes (`TESTER_VERIFIER_FAILURE_PREFIX`, `TESTER_OBSERVATIONS_FAILURE_PREFIX`) live once in `uat/testerVerifier.ts` and are how the stage attributes a failed verdict — never a second copy of the string. Guards: `uat/tester.test.ts` "reports blocking observations when the threshold is set" / "never counts an observation the cap truncated away", `stages/uat.test.ts` "fails uat when a blocking Tester observation was recorded" / "passes uat when observations are advisory (threshold none)".

## [@arch:UAT-OBS-RUNS] UAT Tester runs — partial, failed spin, coverage record, observed-nothing

Split out of `arch:UAT-OBS`.

**A PARTIAL run (T663) is advisory in exactly the same way and still never passes or fails by itself.** Only a call that is STOPPED is partial: the soft time budget (75% of the hard deadline) arms the call's own abort, and the hard deadline is the backstop. The lane then records what the run had already STREAMED (parsed silently — console text is not the agent's answer) and, only when that stream held something but no findings array, sends ONE re-ask with the run's own output quoted back (`buildWrapUpNudge`) — a fresh headless call has no session memory, so a bare "report what you observed" would be contextless; a stopped run that produced NOTHING is not re-asked at all. `uat.tester.tokenBudget` (fresh tokens, read from the same `token_usage` ledger the Inside row's token pill reads) is a POST-HOC report — usage is only known once a call settles, so it names the cause of a stopped run's partial result and is never a reason to discard a FINISHED call's answer or to spend another call on it. The run is recorded `partial` (`process_runs.result_kind = 'partial'`, `failure_detail` naming the cause); the threshold above counts its observations unchanged, and a partial run with none reads "timed out — no observations recovered", never "0 observations — advisory", so it can never read as a clean pass. Guards: `uat/tester.test.ts` (the T663 describe block, incl. "records a COMPLETED over-budget target normally — never partial, never re-asked"), `stages/uat.test.ts` "records a stopped Tester as partial, warns, and still passes uat on green gates" / "a partial Tester run that recovered a blocking observation still fails uat", `model/inside/gates.test.ts` "renders a partial Tester run with its named cause".

**A failed service spin is a BLOCK, never a verdict** (D155, `@arch:UAT-SERVICES`). Before the Tester runs, UAT starts the ticket's services; if one never becomes healthy, the stage parks `boot-failed` with the start failure's health evidence and the Tester does not run. This is an environment fault — nothing about the ticket's code was judged — so it must not become a `failed` verdict, which would route to `fix` and spend a recovery round on a missing binary or an occupied port. A Stop that cancels the spin is `{ kind: 'stopped' }`, not `boot-failed`.
**Coverage record (advisory, both lanes).** The Tester and the review findings lane each end with ONE `info` entry titled `COVERAGE (reported): PASS|SKIPPED|NOT RUN — …` saying what was checked and what was skipped and why (`model/coverageRecord.ts`, shared). It is the agent's self-report ("reported", never "verified"): the Tester's lane and the findings lane persist it as an ordinary info row (the dashboard's findings expansion shows it) but strip it before anything aggregates, so `aggregateUat` / `aggregateReview` never see it, it is appended after the observation cap, and `countBlockingObservations` plus the dashboard's blocking counts exclude it even at `blockingSeverity: info`. When the agent returns none the host adds a deterministic `NOT RUN — the agent reported no coverage record` entry, so silence is never ambiguous. It replaces the old single "unreachable" info observation: an unreachable surface is a `SKIPPED` line inside the record.

**A Tester run that observed nothing** (T861). A target observed nothing when its coverage record is `SKIPPED` or `NOT RUN` (the host fallback included) and it kept no other observation; a run observed nothing when EVERY asked target did. Such a run returns `{kind:'skipped'}`, is recorded `process_runs.result_kind='skipped'` (`status` stays `passed`; the coverage rows are kept) and the Inside Tester row reads `Tester skipped — <reason>` in the amber waiting tone. `uat.testerObservations.onSkip` decides what happens next: `pass` (absent = `pass`, byte-identical to before) passes UAT; `reask` re-asks the skipped targets ONCE with the harness hint prepended to the Tester prompt (a new `process_runs` row), then passes; `reask-then-park` re-asks, and a second skip parks UAT `blocked: tester-skipped`. That block is never a failed verdict and never opens a fix round; the banner offers `Re-run tester` (clears the block and drives UAT again, which follows the same `onSkip` rule) and `Accept skip` (commits a passed UAT verdict and logs `uat: tester skip accepted by user`).
END_DOC_BLOCK: [@arch:UAT-OBS-RUNS]

## [@arch:UAT-SERVICES] UAT starts the ticket's services before the Tester and stops them after, and a failed spin is a `boot-failed` block

Browser UAT needs a running app: the Tester's whole job is to exercise the running application (UI, CLI, API), and the deterministic gates cannot see whether a dev server ever came up. Servers are therefore deferred until a stage needs them (`extension.ts`), and the stage that needs them is `uat` — nothing else spins.

**When.** In `workflow/stages/uat.ts`, after the required gates PASS and after the baseline-review check (a failing gate or a baseline-review block keeps precedence), and BEFORE the Tester. `spinTicket` is called unchanged — `hot` is the ticket's `selectedRepos` filtered to runnable ones (`runnableSubset`, the same pick the dashboard's Services panel uses). The worktrees already exist, so `createWorktree` adopts them, and the manifest's baseline dependencies come up through `ensureBaseline`. No runnable repository in scope, or no Tester configured → no spin and no stop, and the Tester still runs.

**Who owns the stack.** Before spinning, UAT reads the ticket's `servers` rows. If EVERY runnable unit in scope is already `running`, the user owns that stack: UAT neither spins it nor stops it. Anything less than the whole stack is UAT's — `spinTicket` stops every ticket server first, so a partial user-started stack is not restored afterwards.

**Stop.** On every exit path — pass, fail, unreadable, a throw, or a spin that failed partway — a stack UAT started is stopped (`stopTicketServers`) in a `finally` that also wraps the spin itself. `spinTicket` leaves the services it already started running when a later one fails (only a cancel tears its own run down), so a `boot-failed` park must still stop whatever came up. Rows stay offline, so the dashboard offers Restart. Review does not spin or stop anything (its lint/build gates need no running app) and presents no Services row (`@arch` registry). A fix→uat loop re-spins on each pass; the stop is idempotent.

**Failure.** A spin that fails (a service never healthy) parks `uat` BLOCKED with the existing `boot-failed` kind, carrying `startHot`'s health evidence ("nothing is listening" / "pid N listens but never answered" plus the service log tail). The Tester does not run. A generic Resume re-drives uat and retries the spin. A Stop that cancels the spin is `{ kind: 'stopped' }`, never `boot-failed`. The spin/stop seams are `UatDeps.spin`/`UatDeps.stopServers`, wired by `workflow/driveTicket.ts` to `runtime/spin.ts`'s `spinTicket` and `runtime/supervisor.ts`'s `stopTicketServers`; absent (unit tests, the dashboard's gate-option resolver) → no spin, exactly like an absent Tester.

**The Tester's prompt** (`workflow/uat/tester.ts`) lists each running service as `repo/service → http://host:port` and tells the agent not to start, restart or stop anything — the raw start command and "you may stand it up" are gone, because they contradicted `SERVERS_VIA_CLI_RULE`. A serviceless target is told its change is NOT live in any running app of this ticket.

Guards: `stages/uat.test.ts` "spins the ticket runnable services before the Tester and stops them after a pass" / "parks boot-failed with the health evidence when the spin fails, never runs the Tester, and stops the services it already started" / "treats a cancelled spin as a Stop, never boot-failed" / "does not spin when a gate fails" / "runs the Tester with no spin or stop when the ticket has no runnable repo" / "spins only the runnable repos of a mixed selection" / "reuses a fully user-started stack: no spin and no stop" / "owns a partial stack: it spins and stops" / "stops the services when the Tester parks the stage" / "re-spins and stops again on a second UAT pass"; `uat/tester.test.ts` "names the target repository, its base branch and the running services with their live URLs" / "tells a serviceless target its change is not live in any running app"; `driveTicket.test.ts` asserts the seams default to the runtime implementations.

## [@arch:REVIEW] Review findings decide review: R6 fails, R6b blocks on an unreadable answer

`aggregateReview` (`workflow/review/aggregate.ts`) numbers its rules; the findings lane owns two of them, and they are ordered after the deterministic gates (R5 — "a red gate always wins the wording", because a failing gate is cheaper to act on than a model's prose).

- **R6 — a blocking finding FAILS review.** The lane's `capability-missing` parks (the core could not be asked: environmental, not a code defect). Otherwise, when the lane `ran` and `review.findings.blockingSeverity` is not `'none'`, any finding at or above the threshold produces a `failed` verdict, which routes to the fix loop. `'none'` disables the verdict but NOT the evidence — findings are still recorded by the caller.
- **R6b — an UNREADABLE answer BLOCKS, it does not fail.** When the lane `ran`, the threshold is on, at least one target's output came back `unreadable` (`findings.ts`'s `FindingsParseShape`), and NOT ONE finding was read across all targets, review is `blocked` with `blocker: 'capability-missing'` and a reason naming the targets. It closes the original bug: a core answering in prose parsed as zero findings and passed review vacuously into `ship`, which has no `failed` edge, stranding real `high` findings. It blocks rather than fails deliberately — an unreadable answer is the CORE misbehaving, not the code — so it must not spend a fix round.

The parser's half is `findings.ts`'s extraction fallback, gated on "no findings-CARRYING container was recognized" (never "nothing parsed at all"), so narration, a bare-scalar line, a provider envelope, or a tool-echo array (`["bash","-lc",…]`, T694) cannot hide a real finding. It also repairs a model's unescaped `"` in a string value and reads the report from the tail; every promoted value still passes `JSON.parse`, so a genuinely unreadable answer still blocks. Note R6b's conjunction: a run that read SOME findings is decided by R6 on what it read, not blocked on a sibling target's unreadable answer.

## [@arch:REVIEW-SNAPSHOT] Review lanes read a worktree snapshot; UAT and quota parks

Split out of `arch:REVIEW`.

**Both gate lanes review a worktree SNAPSHOT, so uncommitted work is always in scope.** Impl finishing without commits is correct — ship owns committing — and review runs BEFORE ship, so on the normal path the ticket's work is uncommitted when the reviewer is asked about it. Both the UAT Tester (`workflow/uat/tester.ts`) and the Review findings lane (`workflow/review/findingsLane.ts`) therefore call `createReviewSnapshot` (`workflow/reviewSnapshot.ts`) UNCONDITIONALLY whenever a git runner is available: it builds a disposable `refs/karst/snapshot/...` commit carrying committed AND uncommitted (and untracked) content as one tree, never touching the branch, HEAD or index. The findings lane does this regardless of `review.openChanges` — that flag's surviving meaning is whether the stage opens the diff view (`stages/review.ts`), never the diff range. A snapshot failure degrades safely: `createReviewSnapshot` returns `null` and the lane falls back to the branch-based range with a debug line. Guards: `uat/tester.test.ts` "the prompt carries the snapshot range when a snapshot succeeds"; `review/findingsLane.test.ts` "creates a snapshot whenever a git runner is available, even with openChanges absent" / "the prompt built with a snapshotRef agrees with the scope block and omits the committed-only sentence".

**UAT parks on the identical situation (UAT-19).** `workflow/stages/uat.ts`'s Tester lane (`workflow/uat/tester.ts`) shares R6b's parser and used to diverge from it: every target answering `unreadable` closed the Tester's process run `failed`/`unreadable-output`, but the STAGE only warned and let the (already-green) gates decide — passing the ticket on an answer nobody could read, discarding whatever the Tester actually observed. UAT-19 aligned the two lanes: an all-unreadable Tester answer now parks the UAT stage `blocked`/`capability-missing`, exactly like R6b, for the same reason — the core answered and the shape was wrong, which is the core misbehaving, not a fact about the ticket's code, so no `maxFixAttempts` attempt is consumed and no recovery round opens. Before it parks, `runUatTester` gives the target ONE reformat nudge (a second, distinct re-ask from the silence nudge): it quotes the target's own prose back, bounded through `collapseDiagnostic` before it re-enters the prompt, and asks only for that same finding reshaped as the JSON array — no new testing, no new observation — so a genuine, already-found defect (the case that motivated UAT-19: ticket 451's dangling-reference finding) is recovered instead of parked away over a formatting slip. Only a still-unreadable answer after that retry parks. `execution-failed` (the call itself could not be made — environmental, nothing observed) stays advisory in BOTH lanes and must not be collapsed into the same branch as an unreadable answer again — the two are not the same event. The raw unreadable answer is never discarded: `runUatTester` bounds and sanitizes it once (`collapseDiagnostic`) and returns it as `preview`, which the stage writes into its artifact log — never into a verdict reason, a debug line, or `uat_findings` (that table holds only parsed observations). This is a real, unmeasured-rate decision (the reformat-nudge rate, `docs/arch/prompt-metrics.md`'s rollback trigger, starts at zero rows); the fallback if the park fires too often is reverting to advisory, not tuning the nudge's wording first.
**A quota-exhausted lane PARKS (K11, D158).** A review/UAT call that dies on quota stops its lane — `runFindingsLane`/`runUatTester` return a `usage-limited` outcome (not a `crashes` entry, not a T663 partial) — and `aggregateReview`/the UAT stage park `blocked`/`usage-limit` BEFORE R5/R6/R6b. No sibling is judged, no attempt spent; the park row (`@arch:V82`) carries provider/model and sibling answers (`keptOutcome`). Reason `usage limit — <provider> <model>`; `resumeBlockedStage` refuses it. D159 offers 'Pick agent/model…', 'Retry same', 'Dismiss' to re-run only the parked lane with a one-shot override, or dismiss into fix.

## [@arch:PAUSE] Pause: a ticket that starts nothing on its own

`tickets.paused_at` (v52; `null` = active) is the ONE flag that says "karst starts no new work on this ticket". Written only by `pauseTicket`/`unpauseTicket` (`store/tickets.ts`), same single-writer discipline as `setStage`.

Pause is a REFUSAL TO START, never a kill:

- **Interactive terminals stay open.** The user is looking at them; closing them would destroy the very context the pause exists to preserve. Pause stops karst from *launching* sessions, gates, graph nodes and ship sagas — it does not reach into what a human already has on screen.
- **No stage, verdict or run row is rewritten.** A `running` graph run stays `running`; a stage stays where it is. Unpause therefore needs no recovery step — the ticket simply becomes schedulable again.

Every automatic entry point checks it, each at the one read it schedules from — so a fifth trigger cannot slip past by construction:

| Path | Where the refusal lives |
| --- | --- |
| Stage driver (all triggers: hook, sweep, session close, resume) | `driveTicket` at its entry (host-agnostic, so it holds under vitest), and `maybeDrive` again so the trigger is logged as skipped |
| Background sweep selection | `ticketsToSweep` (`workflow/driverController.ts`) |
| Graph coordinator scheduling | `activeGraphRunIds`'s SQL (`coordinator/sweep.ts`) — `AND t.paused_at IS NULL` |
| Graph continuation (planners, nodes, relaunches) | `driveGraphRunContinuation` in `extension.ts`. Reconcile still RUNS — it only probes liveness and spends no tokens, so a paused ticket stays accurately reconciled |
| Stranded-ship recovery at activation | The activation loop, before `runShipSaga` |

Surfaces: `ticketGlyph`/`stageBadge` read it first (gray, "Paused" — a paused ticket is never amber "needs you", because nothing is waiting on the user). The dashboard's ⋯ menu carries Pause/Resume plus a header pill, `karst.pauseTicket`/`karst.unpauseTicket` carry the same seam for the palette, `karst test pause|unpause` drives it in tests, and `karst context` reports `paused`/`pausedAt` so an agent can see it too.
END_DOC_BLOCK: [@arch:PAUSE]

## [@arch:AUTOSTART] Sub-task autostart: queuing, claiming, and orphan requeue

Sub-task auto-start (plan §A, v64) is a tri-state on `tickets.autostart_pending` (`src/store/autostart.ts`): **0 none**, **1 queued** (at scope), **2 starting** (claimed by one sweep, `autostart_claimed_at` stamped). A sub-task holds a concurrency slot (`HOLDS_SLOT_SQL`) when it is not archived AND either its `stage_current` is one of `SLOT_STAGES` (`impl`/`fix`/`uat`/`review`) or it is mid-start (`autostart_pending = 2`); `ship`/`done` and archiving free the slot (archiving also zeroes `autostart_pending`). Two caps from the manifest `subtasks` block (defaults 2 per parent / 4 per project, `0` = unlimited): `perParent` counts a parent's direct children in slots, `total` counts every sub-task in the project in a slot, nested included. `autostartCapsFrom(currentManifest())` is read on every sweep, so a Settings save applies on the next tick.

- **Queue (→ 1)**: written in the creating INSERT (`createTicket`'s `autostartPending`, which `createSubtask` sets from `start ?? true` — CLI `--no-start` passes `false`, leaving the child at scope for a manual Start), or later by `queueAutostart` (0 → 1 only, only at `scope`, not archived; never touches a starting claim).
- **Claim (1 → 2)**: `claimAutostart` is ONE `UPDATE` whose WHERE re-counts both caps against live rows, so overlapping sweeps and other windows can never overshoot them or claim the same child twice; exactly one caller sees `changes === 1`.
- **Leaving scope (→ 0)**: `setStage` calls `clearAutostartOnScopePass` when the `scope` stage is patched `passed` OR `bypassed` — the single place a started child's state clears, so a CLI start and a host start agree.
- **Failed start (2 → 0)**: `releaseAutostart` is guarded on `autostart_pending = 2`, so it only bites when the start failed BEFORE scope passed; if scope already passed, `setStage` cleared it and the release is a no-op. No retry — the same failure would repeat every tick; the user starts the child manually.
- **Orphan (2 → 1)**: a claim still at scope whose `autostart_claimed_at` is NULL or older than `STALE_CLAIM_MS` (10 min) belongs to a window that died mid-start; `requeueStaleClaims` re-queues it at the top of each sweep.

**Orchestration** (`src/extension/ops/subtaskAutostartOps.ts`, `makeSubtaskAutostart`): its own 2 s `setInterval` in `extension.ts` (`SUBTASK_AUTOSTART_INTERVAL_MS`), plus one boot sweep at activation — never the external-change observer. Per sweep, in the window's bound project: requeue orphans, then `pickSubtasksToStart` (`src/workflow/subtaskAutostart.ts`, read-only) selects queued, non-archived children at scope whose non-archived parent is itself in a `SLOT_STAGES` stage (before that the parent's branch may not exist), ordered blocking-first then by id, skipping parents this window does not own (`ownsParent` = `sessions.isLive`) — so a parent with no live session anywhere leaves its children queued. Each pick is claimed, then started through the host's `startTicket` with `pullBase: false` (the child's base is its parent's branch) and `quiet: true` (this op owns the one warning). A lost claim is a silent debug line. A failed start (result `ok: false` or a throw) releases the claim, raises one `notify.warn`, and posts a host `kind='event'` row to the parent whose body is `<key> autostart failed: <reason ≤ 300 chars> (stayed at scope — start it manually | is at <stage> without a session — open its session)`; a failed post is only debug-logged.
END_DOC_BLOCK: [@arch:AUTOSTART]

## [@arch:MAILBOX] Mailbox events: parent–child messaging and wake decisions

The mailbox (`ticket_messages`, v64; store `src/store/ticketMessages.ts`) carries two row kinds: **messages** (`kind='message'`, agent-posted via `karst message send`, `from_ticket_id` = the sender) and **events** (`kind='event'`, host-written, `from_ticket_id = NULL`). The recipient (`to_ticket_id`) of a message is the sender's direct parent OR a direct child (`model/ticketMessaging.ts`); every event goes to the child's parent. Both kinds carry a prose `body` (trimmed, ≤ `MAX_MESSAGE_BODY` 4096), `created_at`, and `read_at` (NULL = unread; set by `karst inbox` via `markRead`). `woke_at` is the wake CLAIM timestamp — set once by `claimWake` when a sweep takes the row's terminal wake decision (`wake` OR `skip`); NULL = undecided.

**Events written at the source.** `setStage` (`store/stages.ts`) derives the row with `subtaskStageEvent` (`store/stageEvents.ts`) from the pre-patch state, inside the same `stage_write` savepoint as the write, and posts it best-effort (a post failure goes to `onEventError`, never fails the stage write). Only a sub-task with a resolvable parent emits, and only on an EDGE, never on a re-patch. Exactly two bodies come from `setStage`: `<key> landed (done)` when `done` goes to `passed` from anything else, and `<key> blocked at <stage>: <reason ≤ 300 code points>` when a block of a NEW kind is set and `blockNotifiesParent(kind)` (`src/model/blockerNotify.ts`, the exhaustive `BLOCKS_NOTIFY_PARENT` record) is true — the routine waits `awaiting-merge`, `awaiting-impl-marker` and `awaiting-subtask` are not announced. The third event shape, `autostart failed`, comes only from `subtaskAutostartOps` (above). `classifyStageEvent` reads a body back as `landed`/`blocked`/`other`; only the first two can wake.

**Delivery sweep** (`src/extension/ops/messageDeliveryOps.ts`, `makeMessageDeliverySweep`, its own 2 s interval `MESSAGE_DELIVERY_INTERVAL_MS`) does two jobs per tick in the bound project:

1. **Pointer** — per RECIPIENT (parent or child), from `unreadByRecipient`. A recipient whose highest unread id is above this window's in-memory watermark gets ONE pointer line through `makeTerminalDelivery` (`src/workflow/messageDelivery.ts`) — fixed text, the unread count and the `inbox` command, never a body or sender — at most one per `POINTER_INTERVAL_MS` (30 s); rows inside the window coalesce into the next pointer. A later message nudges again once its id advances past the watermark. A recipient with zero unread is pruned from the watermark/rate maps (only when the read was not truncated at `DELIVERY_READ_LIMIT`), so its next message nudges immediately. Delivery returns `deferred` — retried next tick, watermark unchanged — when the recipient is not live in this window, its session is graph-owned, the nudge fails, or a LITERAL cli/db/manifest path carries a shell metacharacter (`messagePointer` returns `null` rather than escape). That last case defers the POINTER only; it has no bearing on waking.
2. **Wake** — `pendingWakeEvents` reads event rows with `woke_at IS NULL` and `id > eventBaseline` (`maxMessageId` at sweep construction): events written before this window's activation never wake here. Each is decided by `parentWakeDecision` (`src/workflow/parentWake.ts`), then aged and cooled by the sweep.

## [@arch:MAILBOX-WAKE] Mailbox wake decision, repair and fix briefs

Split out of `arch:MAILBOX`.

**`parentWakeDecision`** returns `wake | skip | retry`. `skip` (terminal): body classifies `other`, parent missing or archived, parent at `ship`/`done`, or a graph ticket (graph surface or a graph approach — `openSession` would start a graph run). `retry` (transient): parent not at `impl` (only `impl` wakes — a `fix` session needs the fix launcher's assignment), parent live here (or its open is in progress), `agent_state` `running`/`waiting` (live elsewhere), integration in flight; a `blocked` event waits only while an `awaiting-subtask` park carries an integration reason (`isIntegrationParkReason`); a `landed` event waits while ANY `awaiting-subtask` park exists or while blocking children are still open (`openGatingSubtasks(..., 'leave-impl')`). Otherwise `wake`. The sweep then turns any non-skip older than `EVENT_MAX_AGE_MS` (30 min, from `created_at`) into a skip, and a `wake` within `WAKE_COOLDOWN_MS` (60 s) of this window's last wake of that parent into a retry. `wake` and `skip` are claimed with `claimWake` (`UPDATE … WHERE woke_at IS NULL`), so across windows exactly one sweep acts per row; `retry` stays unclaimed. A wake runs `karst.openSession` with `{ reveal: false, recovery: true }`; a failure is a `warn`.

**Repair.** v64 is unreleased and early v64 DBs have `ticket_messages` without `woke_at`/AUTOINCREMENT. `migrate` calls `repairTicketMessages` (`store/ticketMessagesRepair.ts`) both at the end of the v64 step and, for a DB already stamped 64, when `ticketMessagesNeedsRepair` says so: it renames the old table, recreates it from `TICKET_MESSAGES_DDL`, copies every row with its id (`woke_at` kept if present, else NULL), drops the old table and ensures both indexes. Idempotent; a no-op when the table is absent or already current.
**Fix briefs share the route, not the table (@arch:V77).** A fix round that reaches a LIVE session no longer types its brief: it stores a snapshot in `fix_deliveries` and sends ONE fixed pointer line (`karst: fix brief #<id> ready - run node <cli> fix-brief --ack …`) through the same per-core route as mail — Stop-hook block (claude, codex), plugin `session.idle` (opencode), typed (opencode2, agy). `makeHookReply` answers the fix pointer BEFORE mail (one block per Stop chain; `blockedAtFix` is separate from `blockedAt`); the hook never reads `agent_state`, only the sweep does, and nothing is typed into a running turn on any core. The agent's `fix-brief --ack` read is the receipt; `fixDeliverySweep` owns the typed first send, re-arm on a session-generation change, the 60 s armed fallback, one typed re-send at 5 min and needs-you at 15 min. A closed session still gets the brief in the launch seed, and a confirmed fix launch marks the snapshot read (`delivered_via='seed'`).
END_DOC_BLOCK: [@arch:MAILBOX-WAKE]

## [@arch:SINGLE-WRITER] Single-writer stage mutation

All stage mutation via `setStage`; agent_state via `setAgentState` (single-writer).

`setStage` is also the ONE clear seam for a usage-limit park (K11, `@arch:V82`): inside its `stage_write` savepoint, when the row's PRIOR `blocked_kind` was `usage-limit` and the patch sets `blockedKind` to anything else (null OR another kind), it resolves the matching open `usage_limit_parks` row (`resolution` from `SetStageOptions.parkResolution`, default `'cleared'`). Every clear path — `clearStageBlock`, a re-run, send-back, `retryGate`, a sub-task integration overwrite, `resetStage`, the CLI `set-stage` — therefore resolves the park without a second writer. `parkGateStage` writes the park row in the SAME transaction as the block (`ParkGateStageInput.park`), never a separate call. `reopenUsageLimitPark` is the inverse for a claim whose re-run ended WITHOUT a verdict (a Stop, or a throw before the lane reported): it nulls the row's resolution and re-blocks through `setStage` in one transaction, because a claim that never produced a verdict must not consume the user's only recovery control.

## [@arch:SHIP-SECRET] Ship refuses to publish an untracked secret-shaped file, and a tracked file is the escape hatch

Ship stages the entire worktree — `prepareCommitInQuarantine` runs `git add -A`, because a stage marker means the agent believes it is done, not that it committed. So a file an agent left behind becomes a commit, a push to `origin`, and a public PR with no human in the loop. Before the commit step, ship scans the `git status --porcelain -uall` output it already reads and refuses the repo when an **untracked** entry matches a deny list of secret-shaped paths — `.env`, `*.pem`/`*.key`/`id_rsa`, `credentials.json`/`.netrc`/`.npmrc`, anything under `.ssh`/`.aws`/`.gnupg`/`.docker`/`.kube`. Only untracked entries are scanned, because a file the repository already tracks is by definition already published; that is also the escape hatch, so a project needing a deliberate `.pem` fixture commits it once by hand and ship never looks at it again. The rules are path-shaped, never content-shaped: reading file bodies would cost a read per ship and produce false positives on the repository's own source. The refusal is per-repo — the other worktrees on the ticket still ship, and the aggregate verdict names the one that did not.
END_DOC_BLOCK: [@arch:SHIP-SECRET]

## [@arch:SHIP-EXCLUDE] Three leftovers, three mechanisms: `.gitignore` for untracked, `ship.exclude` for tracked-but-must-not-ship, `KARST_EXCLUDE_RULES` for karst's own output

Ship's sweep commit stages the whole worktree, so anything dirty ships unless something stops it. Which mechanism applies depends on what the leftover IS. An **untracked** file the agent left behind belongs in the repository's `.gitignore` (or is refused by the deny scan when it is secret-shaped, `arch:SHIP-SECRET`) — ignore rules apply to it because git has not started tracking it. Karst's OWN output (`.karst/`, adapter plugin/skill dirs) is covered by `KARST_EXCLUDE_RULES` written to `.git/info/exclude`, again untracked. But a file the repository **already tracks** and that must not ship — a build artifact (`dist/**`) rebuilt locally for yalc testing, a lock file pinned to a local stand-in — cannot use either: ignore rules never apply to tracked files, which is exactly the hole `repos.<name>.ship.exclude` fills. The key is a list of git pathspecs (glob magic, e.g. `dist/**`); karst prefixes each with `:(glob)` itself and the schema refuses an author-supplied `:` magic.

`prepareCommitInQuarantine` applies the exclude to the QUARANTINE index only: after `git add -A` and before `write-tree`, it runs `git reset -q <preHead> -- :(glob)<spec>...` with `GIT_INDEX_FILE` pointing at the quarantine. The live HEAD, live index and worktree are untouched — an excluded path simply stays dirty in the worktree. Ship logs the excluded paths that were actually dirty (the `git diff --cached` on the quarantine index, before the reset). If excluding leaves the quarantine tree identical to `preHead`'s, no commit is created (never an empty commit) and the repo is treated as a clean worktree — `arch:SHIP-UNCHANGED` still fails a ship where every target is unchanged.

Exclude shapes only the SWEEP commit, never history. An excluded pathspec that also matches agent-COMMITTED changes (`git diff --name-only <base>...preHead`) gets a WARNING, never a block: those changes DO ship, and repo CI is what catches a committed path that must not ship. Committing a path on purpose is the escape hatch for shipping it.

`repos.<name>.ship.regenerate` is the sibling list of shell commands that rebuild the repository's generated files (e.g. `npm run -s docs:graph`). Rebase-on-base runs them (`arch:SHIP-CI-ACTIONS`), and so does every gate pass (UAT/review/fix revalidation) BEFORE the gate list, where the gates run (sandbox for a sandboxed ticket); anything they change lands as one `chore: regenerate generated files` commit, none when nothing changed. Every regenerate run (ok, nothing to commit, no git baseline, failed) records a `regenerate (<repo>)` evidence row (index -1) listing each command with exit code and duration plus the committed paths, shown in the Gates list; a skipped one (no manifest, no repo match, empty list) logs `[gate] regenerate (<repo>): skipped — <reason>`. The manifest entry is found through the target's manifest names (the target repo is a repo path, not a key). A generator that runs and fails is recorded as the gate-like result `regenerate (<repo>)` and that repo's gates are skipped in the pass (they would only add a misleading "is stale"); one the sandbox cannot run (exit 127 or a missing module) parks `capability-missing` naming the command and both remedies (`sandbox.setup`, or the per-command host-only form `{ run, sandbox: host }`) like `arch:GATE-CAPABILITY`. The sweep commit never runs them.
END_DOC_BLOCK: [@arch:SHIP-EXCLUDE]

## [@arch:SHIP-UNCHANGED] A ship in which EVERY target is unchanged is a failure, not a pass

A multi-repo ticket legitimately leaves most of its repos untouched, so each repo's own "no changes from `<base>` — nothing to commit" note is correct and stays. What is not correct is passing when **every** target is unchanged: that ship produced no commit, no push and no PR at all, which is the shape a ticket takes when its work landed somewhere other than its branches — an implementation run that committed into the main checkout, or a stale worktree mapping. Left passing, it walked a ticket through UAT, review and ship to `done` fully green with nothing shipped. Ship now throws after its repo loop when the no-change count equals the worktree count, so the ticket parks at `ship` with the reason on the stage row. A repo skipped because it already carries a live PR is not counted (it shipped earlier), a repo with no persisted base is not counted (there is nothing to compare against), and a real per-repo failure is raised first, because it is more actionable than the symptom it causes.
END_DOC_BLOCK: [@arch:SHIP-UNCHANGED]

## [@arch:SHIP-PREVIEW] The dashboard previews ship's sweep commit and PR read-only, and never diverges from what ship does

Ship's auto-commit and PR title are invisible until the PR exists, so a repo whose `ship.exclude` missed a rebuilt `dist/**` (or whose `{key} {title}` PR title lint rejects) only surfaces at CI. The dashboard now shows an advisory **Ship preview** while the header's ship slot waits for Confirm/Retry (`confirm`/`retry`), so the user sees it before every ship.

It is read-only: no quarantine, no objects written, no index touched. Per worktree repo it reads `git status --porcelain -uall`, matches the same `:(glob)` exclude specs through `git status -- pathspec`, runs the same deny scan (`arch:SHIP-SECRET`) and renders the commit subject / PR title through the SAME `resolveShipArtifacts` helper ship calls (per-repo conventions of `D141`). It reports `will-commit` / `nothing-to-commit` / `already-shipped` / `blocked`, the files to commit, the excluded files, the committed-match warning of `arch:SHIP-EXCLUDE`, and the deny paths; a per-repo read failure is an `error` string and never blocks Confirm ship. The "ship will fail — no repo has changes" line mirrors `arch:SHIP-UNCHANGED` (only when every target is genuinely unchanged).

Two cases the preview must mirror or it would lie: a live PR is `already-shipped` ONLY when the ticket has no completed ship run — after a `passed` ship (`FIX-46`) ship re-ships, so the preview reports `will-commit` and pushes into the open PR; and a rename whose DESTINATION is excluded still commits the SOURCE deletion (`arch:SHIP-EXCLUDE`), so the commit list names the source.

The facts are host-derived (UI-R31) and recomputed on open, on entering the slot, and on the explicit Refresh intent — never polled. Ship itself recomputes at Confirm, exactly as before; the preview is advisory.
END_DOC_BLOCK: [@arch:SHIP-PREVIEW]

## [@arch:FINDINGS-SCOPE] Findings are scoped to the run that produced them

Findings are append-only and have no resolve path; a clean re-review records no batch at all (`workflow/gates/evidence.ts` returns early on zero findings). Therefore any greatest-`runAt` reduction over a whole ticket re-renders a fixed round's findings forever. Every RENDERED surface keys to the process run instead, through `scopeReviewFindings` / `scopeUatFindings` in `src/model/findingScope.ts`. A round in flight (`endedAt === null`) with nothing recorded renders nothing — not the round it replaced.

`uat_findings.process_run_id` is `NOT NULL`, so UAT has no fallback; `review_findings.process_run_id` is nullable and never backfilled, so review falls back to the newest batch of unattributed rows only. Two deliberate non-consumers: the ship stage's findings row and the review rerun's sibling-findings read, which scope by the review stage's `attempt` AND the current review cycle (`currentReviewCycleStart` / `scopeCycleFindings`: `attempt` resets to 0 on send-back, reset, PR-feedback and gate retry, so a bare attempt mixes cycles; a cycle opens at a review run whose attempt dropped, or held after a pass), under the ruling in `ui/dashboard/stateEvidence.ts`, and the fix-brief readers (`extension.ts`, `context/ticketContext.ts`, `cli/fixBriefCommand.ts`), which want the batch being fixed.
END_DOC_BLOCK: [@arch:FINDINGS-SCOPE]

## [@arch:EVIDENCE-STATE] Evidence is not the current state

Every evidence table — `gate_runs`, `process_runs`, `review_findings`,
`uat_findings` — records that work FINISHED. None of them can say a stage is on
a new invocation that has produced nothing yet, and reducing them to "the
newest row" answers a re-entered stage with its PREVIOUS round's rows. That is
what rendered a fixed round's red gates and blocking findings as round 2's live
ledger.

`stage_runs` (v25) is the one table written at stage ENTRY (`openStageRun`,
before the first gate starts), so it is the only thing that can state the
current invocation. Every surface that presents a gate stage's CURRENT state
resolves it through `model/inside/currentAttempt.ts`:

- **no `stage_runs` row for the stage** — pre-v25 or never ran: the
  latest-by-`runAt` reduction stands, byte-for-byte;
- **the stage row was re-entered after the newest run started** — the current
  invocation has opened nothing: the ledger is EMPTY, and the predecessor's
  rows are history reachable through the round switcher;
- **otherwise** — that stage run's rows are the live picture.

A reader's explicit round-switcher selection always wins over this: choosing a
past tab is a deliberate request for a settled attempt.

**The re-entry window is not one driver tick — it spans a full out-of-process
round trip, with two tails that are unbounded.** `fix` is a human boundary the
driver itself never crosses (`workflow/driver.ts`'s `runOneStep` returns
`blocked` for it); the fix→uat transition is authored OUT OF PROCESS by the
`karst stage fix pass` CLI marker (`cli/stage.ts` → `markFixDone`), and
re-entry into the driver after that depends on `maybeDrive` (`extension.ts`),
which is hook/sweep-driven, returns immediately for a PAUSED ticket, and whose
own comment acknowledges triggers can be missed ("an unreachable SessionEnd
hook"). So a ticket can sit in the `null` state — re-entered, nothing recorded
yet — for as long as it takes the next sweep or a window reload to notice: a
ticket paused right after the fix marker fires, or one whose hook never
landed, has no other clock pushing it forward. Once the driver does start,
there is no further delay: `openGateRun` (which opens the `stage_runs` row) is
the first statement of `runUat`/`runReview`.

Rendering nothing during that window is therefore not a UI compromise to be
tightened later — it is the correct answer for as long as the window lasts:
absence over a predecessor's verdict, for however long "nothing recorded yet"
remains true.
END_DOC_BLOCK: [@arch:EVIDENCE-STATE]

## [@arch:BASELINE-REVIEW] A baseline image a ticket changed counts only after the USER approves it

Why: an agent that changed the Settings UI, saw the screenshot test fail, ran the update script and committed the new `__baselines__/*.png` made the `visual` gate compare the page with itself (T601, 95db7158). Re-recording is not evidence.

- **Opt-in knob, manifest-only** (like @arch:BLOCKSEV, no Settings UI): `uat.baselineReview.paths: string[]` of repo-relative globs. Absent or empty → the feature is off and nothing below runs. This repo: `['tests/visual/__baselines__/**', 'tests/visual/layout-known-failures.json']`.
- **Detection reads the WORKING TREE** (`workflow/gates/baselineReview.ts`): at UAT nothing is committed yet (ship makes the commit; `gates/commit.ts` only commits the gate OUTCOME). Per worktree: `git diff --name-status <merge-base(ticket base, HEAD)> -- <globs>` plus untracked `git ls-files --others --exclude-standard -- <globs>`; the base is `resolveTicketBaseRef` (`workflow/baseRef.ts`); sha256 is of the working-tree file. A git failure THROWS and parks `capability-missing` — it never reads as "unchanged". A `.json` change that only REMOVES array entries, or deletes the file, is auto-approved (a ratchet that tightens needs no review); image deletions are not.
- **Decisions** are the append-only `baseline_decisions` table (`store/baselineDecisions.ts`): an entry is approved iff its latest row is `approved` for the sha it has NOW, so a later agent edit lapses the approval.
- **The UAT step** (`workflow/stages/uat.ts`, immediately before the Tester): after the gates PASS, any unapproved entry parks `blocked: baseline-review`. A failing gate keeps precedence — no point approving pictures of a failing build. `baseline-review` reuses `stages.blocked_*` (@arch:BLOCKED); Resume is refused and the ticket reads `Needs you`.
- **Gate fingerprint**: when the gate list passes, `uat_gate_passes` (append-only) records `sha256(git diff --binary <merge-base> + sorted untracked (path, sha))` for the attempt. On re-entry with the same fingerprint the gate list is skipped (no second docker run) and the stage goes straight to the baseline check → Tester. Any code change alters it; an uncomputable fingerprint runs everything.
- **Where the user decides** is the blocked banner ("Review baselines"), NOT the uat-report artifact (@arch:SHELF: the shelf is a read over evidence, never a write surface). The artifact only LISTS path, status and decision. The host copies OLD (`git show <merge-base>:<path>`) and NEW (the working-tree file) into `<globalStorage>/baseline-review/<ticketId>/<sha>.<ext>`; the dashboard panel's only `localResourceRoots` entry is `<globalStorage>/baseline-review` and its CSP gets the webview source as `injectCsp`'s media-source argument. Old | New | Difference (CSS `mix-blend-mode: difference`, no dependency). Messages `baseline-approve {blockId, indices}` / `baseline-reject {blockId, index, reason}` carry the block id and entry indices, never a path; the host re-derives the entries, so a forged index is refused.
- **Effects** (`extension/ops/baselineDecisionOps.ts`, one transaction for the rows): everything approved → clear the block and re-drive `uat` (the path Resume uses, which is bypassed for this handler only). Any rejection → a FAILED verdict through the normal gate writer (@arch:RESULTS keeps the earlier gate evidence) → `fix`, reason `Visual baseline rejected: <path>: <reason>` per rejected entry, which the fix prompt carries.

## [@arch:SHIP-CI-ACTIONS] Ship CI actions: send the CI failure to the agent, and rebase on base, are two separate user buttons

Both are host-only, ship-stage, user-clicked actions. Neither is automatic (an automatic ship→fix on a red check is an unbounded fix→ship→fail loop) and neither is on the agent CLI.

- **Send CI failure to agent** (`workflow/ciFailure.ts`, `extension/ops/ciFailureOps.ts`). Available when `sendBackState` is available, the stored rollup `prs.checks` of a current open PR is `failing`, and NO current open PR is `pending` (a pending rollup means CI runs on a head whose result is unknown, so the stored failure may belong to the head before a push). The host runs `gh run view <run> --log-failed` per failing check (`integrations/ciLog.ts`); a check with a null or non-Actions url is named "no Actions log (external check)" and skipped; an in-progress run falls back to failed step names. The excerpt strips ANSI and the gh prefix, keeps error lines plus a capped tail, and is untrusted data. It is written to `ci-failure-<pr>.log` in the artifacts dir (the sandbox mirror exposes it, `arch:AC-34`), and `sendBackToImplement(…, {reason})` moves the ticket to `impl` and posts the short summary plus the path as a host event in the SAME transaction. No new edge (`arch:BLOCKED`, `arch:STAGEMACH`). A `gh` failure is a user error and the ticket stays in ship.
- **Rebase on base** (`workflow/rebaseState.ts`, `extension/ops/rebaseOnBaseOps.ts`). Available when a current open PR has `merge_block='behind'`. Order: refuse while an agent turn is active (re-checked before the push and before the sandbox recreate); refuse with unsynced sandbox commits; host rebase onto `origin/<base>` (conflict → `rebase --abort`, nothing moves); run each command in the repository's `ship.regenerate` list (`arch:FIELDCHK`) and commit the outputs; read the PR head sha from `gh pr view --json headRefOid` and `git push --force-with-lease=<branch>:<sha>`; clear the stored rollup (`clearOpenPrProbe`, so a pre-rebase log can never be sent) and re-probe (`arch:GH-03`); recreate the sandbox through the no-sync Remove path after re-checking for unsynced commits. A rejected lease stops and does NOT recreate the sandbox. A failed recreate leaves the ticket in ship; the push stands.
- **Regenerate before gates.** `ship.regenerate` is not rebase-only: `runGateList` (`workflow/gates/regenerate.ts`) runs it before each repo's gates and commits the output; rebase behavior is unchanged.
- **The only force path.** `--force-with-lease` with an explicit expected sha is the one place karst force-pushes; it is scoped to this action and does not relax "never force" for Deliver-to-PR.
- **Lease sha.** There is no stored PR head sha (prSync keeps the rollup, not the oid), so the head is read from GitHub immediately before the push. A head that moved between that read and the push still fails the lease.
- **Pre-ship stages (impl/uat/review/fix).** Rebase on base is also offered there (own stage set in `rebaseState`; `isSendBackStage` is not widened) for a spun ticket, so a ticket failing its gate on a since-fixed base regression can take the fix. Availability is store-only (worktrees exist, no agent turn running, no PR merged); whether the branch is behind needs a fetch, so the ops fetches and no-ops ("already on base") when the rebase moves nothing. Same order (busy, unsynced refusal, host rebase with abort on conflict, `ship.regenerate`, sandbox recreate without sync) but NO `gh pr view`, push or re-probe: when a PR exists, `needs_force_push` is armed (`armForcePushLease`) so ship's next push is a lease push. The gate is not re-run and the stage is not resumed; the user clicks Resume.
END_DOC_BLOCK: [@arch:SHIP-CI-ACTIONS]
